# 04 · 知识库数据规范

> 管两件事：**条款怎么存**（技术格式）和**条款从哪来**（版权合规）。
> 加条款、导入资料、改索引之前必看。

---

## 一、最小单元：一条条款

知识库的最小单位是**一条控制点/子类**，不是整份标准。例如：

- 等保2.0 的 `8.1.4.1 身份鉴别` 是一条
- NIST CSF 的 `PR.AA-01` 是一条
- OWASP 的 `A01:2021` 是一条

**为什么切这么细**：用户问的是具体问题（"员工共用账号"），
只有切到控制点级别，检索才能精准命中，引用才能精确到条款号。

---

## 二、条款数据结构

存在 SQLite 表 `clauses` 里：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | INTEGER | 自增 | 内部主键，全文索引和向量都按它对齐 |
| `standard_id` | TEXT | ✅ | 所属标准，如 `dengbao_2.0` |
| `clause_id` | TEXT | ✅ | 条款编号，如 `8.1.4.1` / `PR.AA-01` / `A01:2021`。**同一标准内唯一** |
| `title` | TEXT | ✅ | 条款标题 |
| `chapter_path` | JSON 数组 | ✅ | 章节层级，从大到小 |
| `text` | TEXT | ✅ | 正文（原文或摘要） |
| `text_type` | TEXT | ✅ | `original`（标准原文）或 `summary`（我方改写摘要） |
| `summary` | TEXT | ✅ | 一句话要点，30-60 字 |
| `keywords` | JSON 数组 | ✅ | 3-8 个检索词，**必须包含用户可能说的口语** |
| `risk_tags` | JSON 数组 | ✅ | 风险标签，见第四节；没有就填 `[]` |
| `level_scope` | JSON 数组 | ➖ | 仅等保用，如 `["S3","A3","G3"]` |
| `sort_key` | TEXT | ✅ | 排序用，等保要能按章节正确排（程序会自动补零） |
| `enabled` | INTEGER | ✅ | 1=启用，0=停用（停用后不参与检索） |

### 各标准的编号形态

| 标准 | 编号格式 | 例子 |
|---|---|---|
| 等保2.0 | `章节.控制点` 或 `章节.控制点.序号` | `8.1.4.1`、`8.2.3.7` |
| NIST CSF 2.0 | `功能.类别-序号` | `PR.AA-01`、`GV.OC-02` |
| OWASP Top 10 | `A序号:年份` 及子项 | `A01:2021`、`A03:2021-CWE-89` |
| 用户导入 | 程序生成 `IMP-文件名-序号` | `IMP-某标准-001` |

## 三、种子文件格式（`data/seed/*.json`）

```json
{
  "standard": {
    "id": "nist_csf_2.0",
    "name": "NIST CSF 2.0",
    "full_name": "NIST Cybersecurity Framework 2.0",
    "version": "2.0",
    "publisher": "NIST",
    "license": "public-domain",
    "source_url": "https://www.nist.gov/cyberframework",
    "note": "版权与使用说明，会显示在知识库页面"
  },
  "clauses": [ { "clause_id": "...", "title": "...", "...": "..." } ]
}
```

**完整字段说明见 `data/seed/_SCHEMA.md`**（给写数据的人/程序看的）。

### 自动导入规则

服务启动时 `ingest.ensure_seed_loaded()`：

1. 扫描 `data/seed/*.json`，**跳过没有 `standard.id` 的文件**（例如 `risk_terms.json` 是配置不是标准）
2. 对比文件指纹（文件名+修改时间+大小），没变就跳过，变了就重新导入
3. 导入条款 → 重建全文索引 → 重建语义向量 → 递增索引版本号（让检索缓存失效）

## 四、`risk_tags` 允许值

**只能用下面这些，不要自创**（自创的标签不会触发任何逻辑）。

### 高风险三项 —— 会触发 ⚠️ 标注

| 标签 | 含义 | 覆盖范围 |
|---|---|---|
| `encryption` | 数据加密 | 传输加密、存储加密、密钥管理、密码技术、国密 |
| `access_control` | 访问控制 | 身份鉴别、授权、最小权限、账号共享、特权账号、越权 |
| `personal_info` | 个人信息保护 | 收集告知同意、最小必要、敏感个人信息、跨境传输、留存期限 |

### 其他标签 —— 只用于分类筛选，不触发 ⚠️

`audit_log` 安全审计与日志 · `backup_recovery` 备份与恢复 · `vulnerability` 漏洞与补丁
`incident_response` 应急响应 · `supply_chain` 供应链与第三方 · `physical` 物理环境
`asset_mgmt` 资产与数据分级 · `governance` 制度组织与治理 · `training` 人员培训
`network_security` 网络与边界 · `app_security` 应用与代码安全 · `data_security` 通用数据安全
`risk_mgmt` 风险管理 · `monitoring` 监测与持续改进

### 高风险词表（`data/seed/risk_terms.json`）

除了条款上的标签，还有一份**词表**，用于判断"用户的问题里提到了高风险主题"。
格式：

```json
"encryption": {
  "label": "数据加密",
  "emoji": "⚠️",
  "why": "加密措施不到位会导致数据泄露……（这句话会显示给用户）",
  "terms": ["加密", "明文", "密钥", "HTTPS", "数据保密性", "..."]
}
```

**加词的方法**：编辑这个文件 → 知识库页点「重建检索索引」。不用改代码。

## 五、版权与来源（**最重要的部分**）

### 三套标准的收录方式

| 标准 | 版权状态 | 我们的做法 |
|---|---|---|
| **NIST CSF 2.0** | 美国政府作品，公共领域 | ✅ 收录全部 106 个子类的英文原文 + 中文翻译 |
| **OWASP Top 10 2021** | CC BY-SA 4.0 | ✅ 收录官方描述的译文，署名 OWASP Foundation |
| **等保2.0**（GB/T 22239-2019） | **付费国家标准，全文不公开** | ⚠️ **只收录公开流传的控制项名称 + 我方自行改写的要点摘要**。`text_type` 一律为 `summary` |

### 等保2.0 的红线（违反即项目失败）

1. **绝不照抄国标条文**。`text` 字段写的是"这条要求实际在管什么、典型不合格表现是什么样的"，用的是自己的话。
2. `title` 使用公开的控制项名称（如"身份鉴别""数据保密性"）是可以的——这些名称本身广泛流传。
3. 界面上每条等保条款都必须显示 **"要点摘要（非标准原文）"** 标记。
4. `standard.note` 里必须写明：本项目未收录国标原文，请通过正规渠道购买，一切以正式标准文本为准。

### 为什么这么较真

用户是拿这个做合规决策的。如果我们把**改写的摘要**伪装成**标准原文**，
用户拿去跟测评机构对质，发现"标准里根本不是这么写的"，那这个工具就彻底失去价值了。
**清清楚楚说"这是我们理解的要点"，反而更专业、更可信。**

### 用户导入的资料

- 用户可以导入 PDF / Word / Markdown / TXT
- 程序按标题行启发式切分成条款，**编号由程序生成**（`IMP-xxx-001`）
- 导入界面必须提示："编号由程序生成，请自行核对"
- 导入的条款与内置条款在界面上要能区分（见 06 号文档 P2-1）

## 六、索引是怎么建的

改了条款或分词词典后**必须重建索引**，否则检索行为不一致。

```bat
rem 完整重建（全文 + 向量）
.venv\Scripts\python.exe tools\build_index.py

rem 只重建全文索引（快，改了分词词典时够用）
.venv\Scripts\python.exe tools\build_index.py --no-vector
```

### 全文索引（`clauses_fts`）

- 存的是 **jieba 分词后的空格串**，不是原文
  （SQLite 的 unicode61 分词器会把连续中文当成一个整词，必须先自己切）
- rowid 与 `clauses.id` 严格对齐
- 同时统计词频表 `token_df`，用于算 IDF 权重

### 语义向量（`clause_vectors`）

- 模型：`BAAI/bge-small-zh-v1.5`（512 维，ONNX）
- 建索引的文本：`标题 + 摘要 + 关键词 + 章节路径 + 正文前 400 字`
- 存成 float32 二进制，检索时 L2 归一化后点积即余弦相似度
- **模型不可用时只跳过这一步**，关键词检索照常工作

### 索引版本号

每次重建都会递增 `settings.index_version`，检索层缓存据此失效。
如果检索结果像是"旧的"，先怀疑索引没重建。

## 七、加条款的标准流程

```
1. 想清楚要加什么，属于哪个标准
2. 确认版权状态（付费标准只能写摘要！）
3. 按 _SCHEMA.md 的格式写 JSON，或直接在知识库页面导入文档
4. 重建索引
5. 跑 tests\run_eval.py 确认指标没退步
6. 想一条"加了这条之后应该能搜到"的测试问题，加进 tests/eval_questions.json
7. 记 devlog
```

**第 6 步经常被跳过，但它最重要**——加了条款却没有测试题，
下次改动把它弄坏了你根本不会知道。
