## 二、技术选型与理由

| 层 | 选型 | 为什么不用别的 |
|---|---|---|
| 后端 | Python 3.13 + FastAPI + Uvicorn | 用户电脑已装 Python；FastAPI 一个程序同时提供接口和静态页面，省掉单独部署前端；换 Node 或 Java 都要额外装环境 |
| 前端 | 原生 HTML/CSS/JS，零构建 | 不装 npm、不打包、不编译。改完刷新就见效。用户是非技术人员，将来想微调颜色文字，直接改文件就行。用 React/Vue 会引入一整套构建链 |
| 大模型 | Ollama + qwen2.5:7b-instruct | 用户明确要求完全本地跑。qwen2.5 中文好、按 JSON Schema 输出稳、7B 在 12GB 显存上跑 87 token/秒。DeepSeek-R1 是推理模型，输出思维链导致 JSON 不稳 |
| 知识库 | SQLite 单文件 | 几百到几万条条款用不上 MySQL/Postgres。单文件意味着**备份 = 复制一个文件**，这对非技术用户极其重要 |
| 关键词检索 | SQLite FTS5 + jieba 预分词 | FTS5 内置不用装东西；unicode61 会把连续中文当一个词，所以必须先用 jieba 切好再存 |
| 语义检索 | fastembed + BAAI/bge-small-zh-v1.5（ONNX） | 只依赖 onnxruntime（约 50MB），不用装 PyTorch（2GB+）。模型 100MB，首次下载后完全离线。换成 sentence-transformers 就得拖 torch |
| 结构化输出 | Ollama `format` 传 JSON Schema + 服务端校验 | 小模型纯靠提示词保证格式不可靠。约束解码 + 服务端兜底解析，双保险 |

## 四、两个关键设计（改这里之前务必看懂）

### 设计1 · 检索分数必须是**绝对值**

**踩过的坑**：最初用 BM25 打分，但 BM25 的量纲依赖结果集，必须做"结果集内归一化"。
而归一化之后**第一名永远是满分**——于是"今天天气怎么样"也能拿到 0.4 分，阈值形同虚设。

**现在的做法**：

```
关键词分 = Σ(IDF × 匹配度) / Σ(IDF)          ← IDF 加权覆盖率
            其中 IDF = log(1 + 条款总数 / 该词出现的条款数)
语义分   = clip((cos - 0.15) / (0.58 - 0.15), 0, 1)
            0.15 / 0.58 是实测标定值：中文短问句 vs 长条款文本的余弦分布
最终分   = 关键词权重 × 关键词分 + 语义权重 × 语义分   （默认各 0.5）
```

**为什么 IDF 覆盖率能解决问题**：
"的""我们"这种到处都是的词 IDF 接近 0，"身份鉴别""越权"这种稀有词 IDF 高。
问"推荐几部好看的电影"时，分母（所有查询词的 IDF 之和）很大、分子（匹配上的 IDF）很小，
得分自然很低——**实测从 0.395 降到 0.143**。

**标定数据**（改动后必须重新标定）：

| 类别 | 得分区间 |
|---|---|
| 真实合规问题 | 0.44 ~ 0.97 |
| 无关问题 | 0.14 ~ 0.30 |
| 当前阈值 | **0.40** |

### 设计2 · 防幻觉不能只靠提示词

大模型一定会编条款号。四层防线：

| 层 | 在哪 | 做什么 |
|---|---|---|
| 一 | `retrieval.py` | 最高分低于阈值 → 直接拒答，**根本不调大模型**。从源头杜绝 |
| 二 | `prompt.py` | 提示词硬约束：只能引用【可用条款】里出现的编号 |
| 三 | `guard.py` | 服务端校验：模型返回的引用逐个比对检索结果，对不上的剔除 |
| 四 | `guard.py` | 正文扫描：正文里出现的、不在检索结果中的条款号，记入"技术详情"提示用户核实 |

**外加两条鲁棒性处理**：

- **位置序号翻译**：模型爱写"【条款1】"，自动翻译回真实编号（`8.1.4.1 身份鉴别`）。
  注意实现时要收紧正则，别把"第一，要检查…""第三次登录"这类正常中文误改。
- **引用带标题**：模型爱写"8.1.4.1 身份鉴别（复杂度）"，从字符串里提取编号再匹配。

### 设计3 · `found` 和 `need_clarification` 是两件独立的事

**踩过的坑**：qwen2.5 会把"我还想多问几句"表达成"知识库中未找到"，
导致【共用账号】【手机号没加密】这类**明明检索到了条款**的问题，用户被告知"没找到"。

**现在的规则**：

```
found              = 知识库里有没有相关条款  →  服务端按检索阈值判定，不听模型的
need_clarification = 描述够不够具体          →  听模型的，但追问时仍要引用条款、不得说"找不到"
```

服务端还会做兜底：如果模型声称"未找到"但检索明明命中了，就删掉正文里矛盾的"未找到"说法。

## 五、一条提问的完整链路

```
1. 收到问题
2. 客套话？        → 是则直接回引导语，不检索
3. 检索条款        → 最高分 < 0.40 ⇒ 拒答（不调模型）
4. 组装提示词      → 系统规则 + 6 条可用条款 + 最近 6 条历史
5. 调 Ollama       → JSON Schema 约束输出
   └ 不可用？      → 降级为"只列条款"，引用取自检索结果
6. 引用白名单校验  → 剔除非法编号；位置序号翻译回真实编号
7. 正文编号扫描    → 标出可疑编号，写入技术详情
8. ⚠️ 风险判定     → 问题关键词 ∪ 引用条款标签 ∪ (模型自报 ∩ 有文本佐证)
9. 补免责声明、落库
10. SSE 推给前端   → status → session → delta… → meta → done
```

## 六、技术债登记

| 位置 | 问题 | 影响 | 计划 |
|---|---|---|---|
| `app/routers/chat.py` | 流式是"生成完再打字机回放"，不是真流式 | 长答案前 2 秒干等 | P3-1 |
| 全局 | 错误信息用 `print`，没落盘 | 窗口关了查不到 | P1-1 |
| `retrieval.py` | `VEC_FLOOR/VEC_CEIL` 是实测标定值，硬编码 | 换嵌入模型就得重新标定 | 加注释说明，暂不参数化 |
| `normalize.py` | 口语映射表靠人工维护 | 新说法可能搜不到 | 持续补充，已有明显改进立刻加成评测题 |
| 无 | 没有鉴权 | 只监听 127.0.0.1，可接受 | 不做 |

## 七、依赖清单（`requirements.txt`）

| 包 | 用途 | 大小 |
|---|---|---|
| fastapi / uvicorn / python-multipart | Web 服务 | 小 |
| pydantic / python-dotenv | 数据结构与配置 | 小 |
| jieba | 中文分词 | 19MB |
| numpy | 向量计算 | 15MB |
| fastembed + onnxruntime | 本地语义向量 | 约 65MB |
| pypdf / python-docx | 导入 PDF / Word | 小 |

**刻意不引入的**：PyTorch（2GB+）、LangChain（抽象层太重、排查困难）、任何需要联网的向量数据库。

## 八、外部依赖与风险

| 依赖 | 风险 | 应对 |
|---|---|---|
| Ollama 服务 | 可能没启动 | 启动时自动尝试拉起；连不上给人话提示 |
| qwen2.5 模型文件 | 官方源国内下载慢/卡死 | `tools/fetch_model.py` 走国内镜像（41MB/s） |
| HuggingFace 下载 | 国内直连慢、xet 通道 401 | `config.py` 已固化 `HF_HUB_DISABLE_XET=1` + `hf-mirror.com` |
| 语义模型文件 | 可能损坏或缺失 | 加载失败自动降级为纯关键词检索，功能不中断 |
