# 07 · 测试与验收规范

> 这个项目最怕的不是崩溃，而是**"测试通过但答得不对"**。
> 所以测试的重点不是"代码跑不跑得起来"，而是"答得准不准"。

---

## 一、测试分七层

| 层 | 测什么 | 在哪 | 什么时候跑 |
|---|---|---|---|
| **第0层 · 静态检查** | Python/JS 语法、JSON 格式、JS 引用的元素 ID 是否存在、SVG 图标名是否有定义、`.bat` 是否纯 ASCII、独立脚本打印非 ASCII 时有没有把 stdout 切成 UTF-8 | `tests/check_syntax.py` | **每次改完代码，跑评测之前** |
| **第1层 · 检索与判定质量** | 该命中的有没有命中、无关问题会不会误答、库外法规有没有识别、适用性判定有没有拦住、⚠️ 有没有误标 | `tests/run_eval.py --no-llm` | **每次改动后必跑（秒级）** |
| **第2层 · 端到端问答** | 模型真的追问了吗、库外法规声明真的写进回答正文了吗、有没有转述条文 | `tests/run_eval.py`（默认两层都跑） | 改了提示词或回答逻辑后 |
| **第3层 · 异常路径** | 断网、模型挂掉、空知识库会不会白屏 | `tests/test_edge_cases.py` | 改了错误处理或接口后 |
| **第3层 · 纯逻辑单测** | 范围判定、风险标注、口语归一化、流式解析、Word 导出、导入与撤销、质量自检的三态 | `tests/test_scope.py`、`tests/test_guard.py`、`tests/test_normalize.py`、`tests/test_streaming.py`、`tests/test_export.py`、`tests/test_revert.py`、`tests/test_quality_gate.py` | 改了对应模块后 |
| **第4层 · 界面（真浏览器）** | 页面在真 Chrome 里能不能用：JS 有没有报错、axe-core 无障碍扫描、键盘能不能操作、字体加载、手机宽度有没有溢出、抽屉导航能不能开合 | `tests/test_frontend.py` | 改了 HTML/CSS/JS 之后 |
| **第5层 · 人工验收** | 浏览器里亲手用一遍，是不是真的好用 | 手动 | 每次交付前 |
| **第6层 · 模型评审（LLM-as-judge，手工）** | 用本地模型逐题判「忠于条款 / 不编造 / 回答切题」并算幻觉率；judge 自己再用人工标注 5 条校准 | `tools/llm_judge.py`；`tests/run_eval.py` 第二层之后也会跑 | **发布前手工跑**（需要 Ollama，**不进 CI**） |

**第3层和第4层的套件都不依赖 Ollama**，所以它们在任何时候都能跑。
这条纪律是踩过坑才立的：曾经有个"超长问题"的用例同时依赖 Ollama 在线，
而且断言写成了永远为真，长期"假通过"。

### 第4层的由来（语法正确 ≠ 页面能用）

第0层解决了"JS 语法错误"，但语法正确的代码仍然可以在浏览器里崩掉：
元素 ID 对不上、DOM 结构假设错了、事件绑在根本不存在的节点上。
更隐蔽的是 CSS——`.empty-state` 的样式一改，
"HTML 里写了一份空状态、JS 又生成一份"这个重复 bug 才暴露出来。

所以第4层真的拉起一个临时端口的服务、用本机 Chrome 把页面渲染出来再断言。
见 `tests/test_frontend.py`（18 个用例）与 `tests/frontend_probe.js`（只采事实，判定在 Python 里）。

**它的额外前提**：本机要装 Node.js 和 Chrome。缺任何一个会直接判失败并说明缺什么，
**不静默跳过**——静默跳过等于给自己发一张假的通行证。
`tools/cdp_eval.js` 用 Node 自带的 `WebSocket` 直接讲 CDP 协议，
**没有引入 puppeteer / playwright**：这个项目要求零运行时依赖且能离线跑，
测试基础设施不该成为例外。

### 第0层的由来（别跳过它）

有一次 `web/js/kb.js` 里写成了 `dengbao_2.0: '等保2.0'`——
`dengbao_2.0` 不是合法的 JS 变量名（会被解析成 `dengbao_2` 后面跟个 `.0`），
**整个知识库页面在浏览器里会直接失效**。

而当时的验证只检查了"这个文件能返回 HTTP 200"，完全没发现。

所以现在每次改完代码，先跑：

```bat
.venv\Scripts\python.exe tests\check_syntax.py
```

它会检查：Python 语法、`node --check` 校验 JS（`web/`、`tools/`、`tests/` 三个目录）、
JSON 格式、**JS 里引用的每个元素 ID 是否真的存在于 HTML 中**、
以及**JS/HTML 里用到的每个 SVG 图标名在雪碧图里有没有定义**
——这两类错误都只在浏览器里暴露，而且图标名写错时浏览器**不报任何错**，只是画一片空白。

还有两条是跟 Windows 的字符编码有关的，都栽过跟头：

- `check_bat_ascii()`：`.bat` 必须是纯 ASCII。cmd.exe 按**当前控制台代码页**逐字节读批处理
  文件，文件里有中文而代码页不匹配时命令会被撕碎，表现是**双击脚本什么都不发生**。
- `check_console_encoding()`：**不 `import app` 的独立脚本**如果会打印非 ASCII，必须自己把
  `sys.stdout` 切成 UTF-8。原因是 Windows 上标准输出被重定向（管道、写文件、CI 抓取）时，
  Python 按控制台代码页编码：开发机是 GBK，中文编得出来，所以这个缺陷在本地**永远看不见**；
  GitHub Actions 的 windows runner 是 cp1252，打印中文直接 `UnicodeEncodeError` 崩掉进程。
  第一次跑 CI 就是这么挂的（`tests/check_syntax.py` 自己中招）。
  `import app.*` 的脚本由 `app/console.py` 自动修好，所以规则只约束独立脚本。

> 本地想复现 cp1252 环境：`$env:PYTHONIOENCODING = "cp1252"` 再跑一遍脚本。


**为什么第1层最重要**：它是唯一能**自动、快速、客观**反映"答得准不准"的手段。
改任何东西跑一遍，指标掉了立刻就知道。

## 二、指标红线

| 指标 | 红线 | 含义 | 当前值 |
|---|---|---|---|
| **拒答正确率** | **必须 16/16** | 无关问题必须拒答 | 16/16 |
| **库外法规识别率** | **必须 6/6** | 点名了知识库里没有的法规时必须识别出来 | 6/6 |
| **适用性判定拦截率** | **必须 27/27** | "这条对我适用吗"这类问题必须拒绝硬答 | 27/27 |
| **追问正确率** | **必须 4/4** | 描述太笼统时必须先追问再答 | 4/4 |
| 检索召回率 | ≥ 25/25 | 该命中的条款出现在前 6 条里 | 25/25 |
| ⚠️ 风险标注率 | ≥ 8/9 | 该标的风险标上了 | 9/9 |
| ⚠️ 误标率 | **误标 ≤ 0 处** | 不该标的标签一个都不能标 | 0/2（2 道禁止标注题，0 处误标） |
| 单次回答耗时 | ≤ 10 秒 | 端到端 | 1.3 ~ 4.3 秒 |
| 引用真实率 | 100% | 引用卡片里的条款必须都真实存在 | 100%（服务端强制） |

### 四条一票否决项

**宁可答"找不到"，也绝不能编造条款、更不能替用户做适用性判定。**

- **拒答正确率**跌破 16/16
- **库外法规识别率**跌破 6/6
- **适用性判定拦截率**跌破 27/27
- **追问正确率**跌破 4/4

上面任何一条掉了，**不管别的指标多好看，都必须回滚**。

### 为什么数量本身也要卡（`EXPECTED_COUNTS`）

只看"通过数 / 红线数"有个致命盲区：**如果把题库删掉一半，通过数会跟着缩水，
红线却还是显示"通过"**。所以 `app/quality.py` 里同时卡了两样东西——
每一类的题目数量下限，和通过数。加题时两处都要改。

红线定义在 `app/quality.py` 的 `RED_LINES` 与 `EXPECTED_COUNTS`，
**改这里之前先改本文件**。

## 三、怎么跑测试

```bat
rem 第0层：静态检查（最先跑，最快）
.venv\Scripts\python.exe tests\check_syntax.py

rem 第1层：检索与判定质量（快，约 5 秒，不需要 Ollama）
.venv\Scripts\python.exe tests\run_eval.py --no-llm

rem 第1+2层：连大模型端到端（慢，约几分钟；Ollama 没开会自动跳过第二层）
.venv\Scripts\python.exe tests\run_eval.py

rem 第2层只想跑前几题（调试用）
.venv\Scripts\python.exe tests\run_eval.py --limit 6

rem 第3层：异常路径（22 个用例）
.venv\Scripts\python.exe tests\test_edge_cases.py

rem 第3层：质量自检的三态与版本号（4 个用例，自检崩了必须是"未知"而不是"通过"）
.venv\Scripts\python.exe tests\test_quality_gate.py

rem 第3层：范围判定（37 个用例，覆盖范围/库外法规/适用性判定/追问，不依赖 Ollama）
.venv\Scripts\python.exe tests\test_scope.py

rem 第3层：风险标注（19 个用例，含误标回归与编号展开）
.venv\Scripts\python.exe tests\test_guard.py

rem 第3层：口语归一化与分词（10 个用例）
.venv\Scripts\python.exe tests\test_normalize.py

rem 第3层：导入与撤销（10 个用例，用临时数据库，不动真实数据）
.venv\Scripts\python.exe tests\test_revert.py

rem 第3层：流式输出（12 个用例，纯函数，不依赖 Ollama）
.venv\Scripts\python.exe tests\test_streaming.py

rem 第3层：Word 导出（11 个用例）
.venv\Scripts\python.exe tests\test_export.py

rem 第3层：开发日志读写（12 个用例，全程临时目录）
.venv\Scripts\python.exe tests\test_devlog.py

rem 第3层：留出集纪律（指纹锁 / 基准棘轮 / 逐题退步检测）
.venv\Scripts\python.exe tests\test_eval_discipline.py

rem 第3层：等级判定矩阵（240 组合 + 回答侧 18 条句式 + 知识型护栏，不依赖 Ollama）
.venv\Scripts\python.exe tests\test_level_denial.py

rem 第3层：服务端答案拼装与概述过滤（18 个用例；模型不再写正文）
.venv\Scripts\python.exe tests\test_answer_render.py

rem 第3层：组装一致性（18 个用例；逐行穷举，追不到来源就红）
.venv\Scripts\python.exe tests\test_answer_assembly.py

rem 第4层：界面（19 个用例；需要本机有 Node.js 和 Chrome，约 40 秒）
.venv\Scripts\python.exe tests\test_frontend.py

rem 只想快速判断达标不达标（退出码 1 = 跌破红线，可接自动化）
.venv\Scripts\python.exe tools\check_quality.py --quiet
```

**全部套件的退出码都必须是 0。** 一共 **16 个套件**（其中 13 个逐条计数，共 **221 条用例**），
外加 dev 集 **78 题**与留出集 **43 题**的评测。
> 注：`tests/test_level_denial.py`（20 条用例）从 2026-10-19 起在 `.github/workflows/ci.yml` 的「等级判定矩阵」步骤里跑，`tests/test_answer_render.py`（20 条用例）在「服务端答案拼装与概述过滤」步骤里跑，所以上面 **214 条用例**的口径**包含**它们。`test_level_denial` 的 240 句矩阵（`LEVELS × ACTIONS × SUBJECTS`）由 `test_matrix_blocked` 在运行时生成，`test_answer_render` 也不读外部数据文件，两者都不需要 Ollama，**整份都在 CI 里跑，没有「留在本机」的部分**；CI 里唯一不跑的是端到端 / 提示词层（第二层，需要 Ollama），见本节开头的降级声明。报告写到 `tests/eval_report.md`。

> **数字分两层，两层都被 `check_syntax.py` 校验**：总量（16 个套件 / 221 条用例）由
> `_INT_RULES` 比对，单个套件的条数（`` `tests/test_xxx.py`（N 条用例） ``）由 `_SUITE_CASE_RE`
> 比对。只校验总量是不够的——`test_answer_render.py` 从 12 条加到 18 条时，全仓总量同步成了
> 194，而本文档那句「（12 条用例）」一直是三年前的值，没报红。
>
> 还有一条同源约定：**套件打印的「通过 N / M」必须等于它自己的 `@case` 条数**。
> `tests/test_edge_cases.py` 原来在 runner 里额外统计一次「真实库未被改动」，
> 于是打印 23/23 而 `@case` 只有 22 条——两套数字差 1，任何按运行输出回填文档的人都会写错。
> 现在那条守卫本身也是一条 `@case`。

> **红队纪律（写死在这里，别当建议看）**：每发现一种**新绕法**，必须**先**把它变成
> `tests/eval_questions.json` 里的一道 dev 题，**再**动代码修。顺序反了就等于"修完再补一道
> 自己已知答案的题"，题库会重新变成自说自话。留出集**永不复用**这些原句——留出集只在
> 收尾跑一次，重复使用会把它变成第二个 dev 集。


`tests/test_frontend.py` 是最慢的一个（要真开浏览器），所以放在最后跑。
它跟别的套件一样**不依赖 Ollama**，但依赖 Node.js 和 Chrome；
两者缺一时它会立刻失败并打印缺哪个，不会假装通过。
它用的是**数据库的临时副本**，跑测试不会动你的历史记录。

> **注意**：改过 `app/normalize.py` 的 `tokenize()` 或 `COLLOQUIAL_MAP` 之后，
> **必须重建索引**——`FTS5` 里存的是分词后的结果，不重建的话检索还在用旧词表：
>
> ```bat
> .venv\Scripts\python.exe tools\build_index.py
> ```

### 全新检出（CI 和新人第一次跑）

干净 clone 下来没有 `data/app.db`，先跑一次这个把知识库建起来：

```bat
.venv\Scripts\python.exe tools\build_index.py
```

它发现库是空的会自动从 `data/seed` 导入 283 条种子条款，并建好全文索引与语义向量
（实测 3.5 秒，其中大部分是加载语义模型）。**没有这一步，需要知识库的套件全部会失败。**

### CI（`.github/workflows/ci.yml`）

每次 push 到 `main` 和每个 PR 都自动跑：

| 作业 | 平台 | 内容 |
|---|---|---|
| 后端套件 | `ubuntu-latest` + **`windows-latest`** | 11 个套件（含 `check_syntax.py`）+ `run_eval.py --no-llm` |
| 界面回归 | `ubuntu-latest` | `test_frontend.py`（真 Chrome + axe-core） |

几个刻意的选择：

- **后端跑两个平台**。Windows 才是这个项目的主要目标平台（用户双击 `.bat` 启动），
  但 ubuntu 快得多——两个都跑，信号最全。
- **界面套件只跑 ubuntu**：`tools/cdp_eval.js` 的 `findChrome()` 认 Linux/macOS/Windows
  三种路径，界面行为本身与平台无关。
- **语义模型用 `actions/cache` 缓存 `data/models`**。CI 里唯一需要联网的地方就是
  fastembed 下载 `BAAI/bge-small-zh-v1.5`（约 95 MB），缓存命中就不下了。
- **设 `HF_MIRROR=https://huggingface.co`**：开发机在国内默认走 `hf-mirror.com`
  （`app/config.py` 的 `setdefault`），runner 上官方源更快更稳。
- **不跑 `run_eval.py` 的端到端那一档**（需要 Ollama）。CI 里没有大模型，
  这正是铁律三要保证的：**测试不许依赖外部服务是否在线**。

### 输出怎么读

```
检索召回率   25/25    ← 该命中的都命中了
拒答正确率   16/16    ← 死线，不能掉

追问正确率   4/4      ← 死线：笼统问题必须先追问
⚠️ 误标率    0/2      ← 误标 ≤ 0 处
```

## 四、评测集（`tests/eval_questions.json`）

78 道题，分五类（题数与 `app/quality.py` 的 `EXPECTED_COUNTS` 必须一致，`tests/check_syntax.py` 会比对）：

| 类别 | `expect` | 题数 | 用途 |
|---|---|---|---|
| 真实合规问题 | `hit` | 25 | 测召回率（`must_include_any` 里至少命中一条） |
| 完全无关问题 | `reject` | 10 | 测拒答能力（**一票否决**） |
| 点名库外法规 | `out_of_kb` | 6 | 测"未收录"识别与不转述（**一票否决**） |
| 适用性判定 | `undeterminable` | 27 | 测"不替用户下结论"（**一票否决**） |
| 信息不足的问题 | `clarify` | 4 | 测追问（**一票否决**） |

加题时**必须同步改** `EXPECTED_COUNTS` 与 `RED_LINES`：题库与本文件、`docs/00`、`README` 的数字由 `check_syntax.py` 交叉校验，改漏一处静态检查就会失败。

**铁律：红队每发现一种新绕法，必须先把那句原话加进 dev 集，再动代码修。**
顺序反了就会出现「评测 7/7 全绿、真实攻击面照样打穿」——这是本项目已经踩过三次的坑
（t11/t13/t14 三轮都是：修完才补题，补的又是自己想的题）。留出集**永不复用**这些原句，
否则留出集就变成了第二份 dev 集，失去泛化测量的意义。

每道题的字段：

```json
{
  "id": "q01",
  "question": "我们公司十几个人都用同一个管理员账号登录进销存系统，这样有问题吗？",
  "expect": "hit",
  "must_include_any": ["8.1.4.1", "8.1.4.29", "8.2.3"],
  "risk_expect": ["access_control"],
  "note": "账号共享 → 身份鉴别/访问控制"
}
```

| 字段 | 说明 |
|---|---|
| `expect` | `hit` 期望命中；`reject` 期望拒答；`out_of_kb` 期望识别出"点名了库外法规"；`undeterminable` 期望拒绝做适用性判定；`clarify` 期望先追问 |
| `must_include_any` | top-6 里**至少出现一个**这些编号（支持前缀匹配）。留空表示只要求"命中" |
| `risk_expect` | 期望的 ⚠️ 标签。**只填三类高风险，其他标签不参与评分** |
| `risk_forbid` | **不许**出现的 ⚠️ 标签（误标回归用）。判定方式是"假设模型见谁都标"，看这三个标签会不会被标出来 |
| `out_of_kb_expect` | `expect: "out_of_kb"` 时，期望识别出的法规名（子串匹配） |
| `clarify_expect` | 期望先追问 |

### 五类 expect 分别防的是什么

| 类型 | 防的缺陷 | 例子 |
|---|---|---|
| `hit` | 该答的答不出来 | "十几个人共用一个管理员账号" |
| `reject` | 无关问题硬答、编造条款 | "今天北京的天气怎么样" |
| `out_of_kb` | **用户点名库外的法规时凭记忆编造条文** | "《个人信息保护法》第 13 条怎么规定的？" |
| `undeterminable` | **替用户做适用性判定，罗列一份"不适用条款清单"** | "列出等保三级里所有不适用的条款" |
| `clarify` | 描述太笼统时硬答或直接说"找不到" | "我们系统安全吗" |

后两类是 2026-10-08 审计新加的。加它们的原因值得记住：
这两类问题**检索分数都很高**（0.53~0.97），阈值闸门根本拦不住，
而原来的评测集里一道这样的题都没有——所以缺陷存在了很久却一直显示"全部达标"。

### 加测试题的规矩

**每修一个 bug，都要把它变成一道测试题。** 否则下次会再犯。

加题时注意：

- `must_include_any` 不要写太窄。如果一个问题的合理答案有好几个条款，
  就都列进去（用前缀匹配）。**测试写太窄会造成假失败**——
  实际召回的条款是对的，只是因为不在你列的清单里就判失败。
- 用 `expect: "reject"` 的题要真的有把握它是无关的，别把模糊的合规问题放进去。
- **加题之后要同步改 `app/quality.py` 的 `EXPECTED_COUNTS` 和 `RED_LINES`**，
  否则新题不参与红线判定，等于没加。
- `risk_forbid` 只写"真的完全不该出现"的标签。如果被检索到的条款本身
  就带这个标签（比如 `8.1.4.26`「个人信息保护」的 `risk_tags` 含 `personal_info`），
  那么模型真引用了它、标出 `personal_info` 是**正确行为**，不该写成禁止项。

### 留出集：防止"照着测试集调参"（`tests/eval_holdout.json`）

**先说问题**。上面这 78 题（下称 dev 集）是这个项目唯一的评测依据，而阈值 0.40、
关键词/语义权重 0.5:0.5、`COLLOQUIAL_MAP` 的每一批词，全都是**照着它调**出来的。
于是它衡量的已经不再是"系统能不能用"，而是"系统能不能通过这一套题"。
dev 集 6 项指标全绿，**并不能推出**换一批没人调过的题也全绿。

**再说解法**。新增留出集 `tests/eval_holdout.json`（37 题），三条纪律：

| 纪律 | 怎么落地 |
|---|---|
| 考不同的东西 | 条款全部取自 dev 集从未引用过的那一批（283 条里 dev 覆盖 190 条、剩 93 条，用 `tools/eval_coverage.py` 复算）；题干与条款模式都与 dev 集零重叠 |
| 不许偷偷改 | 指纹锁 `tests/eval_holdout.lock.json` 存 sha256；改动留出集会让 `tests/test_eval_discipline.py` 失败，逼你先想清楚"我改的是尺子，还是因为量出来的数不好看" |
| 基准只能升不能降 | 每类的最低通过数记在锁里。变差立刻失败；变好也不会自动涨及格线，要显式 `--raise-baseline` |

```bat
rem 检查（本地与 CI 都跑这个）
.venv\Scripts\python.exe tests\test_eval_discipline.py

rem 有意修改留出集之后，刷新指纹与题数（不动基准）
.venv\Scripts\python.exe tests\test_eval_discipline.py --update-lock

rem 确认当前成绩可作为新基准（拒绝下调，除非 --force）
.venv\Scripts\python.exe tests\test_eval_discipline.py --raise-baseline
```

**怎么读分数**：留出集不看"通过/不通过"，看**与 dev 集的差距**。
dev 100% 而留出 60% 说明在过拟合；两者接近才说明真的学到了通用规律。

**实测结果**（2026-10-10 建集，2026-10-19 修复后复测）：

| 分类 | dev 集 | 留出集（修复前） | 留出集（修复后） |
|---|---|---|---|
| 该命中 | 25/25 | 22/22 | 22/22 |
| 该拒答 | 16/16 | **0/3** | **9/9** |
| 库外法规识别 | 6/6 | 3/3 | 3/3 |
| 适用性判定拦截 | 27/27 | 3/3 | 3/3 |
| 该追问 | 4/4 | —（留出集无此类） | — |
| ⚠️ 误标 | 0 处 | 0 处 | 0 处 |

**当初唯一的缺口就是拒答，而且是同一类问题的两种难度**：dev 集当时的 5 道拒答题是
"今天天气怎么样""推荐几部电影"这种明显无关的，分数天然很低；留出集的 3 道是
"员工的加班费怎么算""纸质合同要保存多少年""产品出口欧盟要不要做 CE 认证"——
**长得像合规问题，但不属于网络安全合规**，检索分数 0.470~0.548，直接越过了 0.40 阈值。
这说明 **5 道拒答题全对（现为 10 道）并不代表拒答能力够用**。

**修复过程（这一段比结论有用）**：

1. 先测分数的构成，发现这些题**关键词分只有 0.097~0.165，语义分却高达 0.84~0.93**。
   `bge-small-zh` 把它们和「人员离岗」「管理制度评审」「合规产品采购」排得很近，
   因为两边都在讲"员工 / 制度 / 保存 / 合规"这层语义。融合分 `0.5*kw + 0.5*vec`
   于是被语义分单独抬过了阈值。
2. 接着试"关键词下限"方案，**行不通**：dev 集里关键词分最低的真题
   「合规要花很多钱吗」是 0.137，比拒答题「纸质合同保存多少年」的 0.165 **还低**，
   两者在关键词维度上重叠，任何单一阈值都切不开（`KW_FLOOR=0.18` 拦得干净但误杀 2 道真题）。
3. 最后改用**领域证据**判定（`app/scope.py: detect_out_of_domain`）：
   **有明确的非本领域词（劳动法、社保、发票、纸质、出口…）且没有任何网络安全锚点
   （账号、日志、备份、服务器…）才拦**。只有前者、没有后者时一律放行——
   宁可漏拦，也不能把「加班时服务器被入侵了怎么办」这种真问题挡在门外。
4. 同时在 **dev 集**补了 q45~q49 五道同类难拒答题（婚假 / 社保基数 / 发票红冲 /
   消防验收 / 三包）作为调参靶子，`RED_LINES.reject_required` 与
   `EXPECTED_COUNTS.reject` 一起从 5 改成 10。**调参发生在这里**，留出集只在最后跑了一次。

> **⚠️ 必须说清的诚实问题**：写这张词表之前我已经看过留出集那三道题，
> 所以这次 3/3 只能算**回归守门**，不能当作"泛化能力已被证明"。
> 真正的泛化证据要等一批没人看过的拒答题。
> 建议由**没读过这份词表的人**再写 3~5 道同类题（行业资质、环保、招投标、税务…）
> 追加进 `eval_holdout.json` 并 `--update-lock`，那一次的结果才是干净的。
> 这条也写进了 `tests/eval_holdout.lock.json` 的 `known_gaps`。

**一条选题教训**："未覆盖的条款"不等于"未覆盖的考点"。初次给留出集选题时有两道题
期望的是 NIST 的 `ID.RA-07`（变更管理）和 `DE.CM-01`（网络监测），结果系统检索到的是
等保 `8.1.5.2` 与 `8.2.5.20`，**正文完整回答了问题**（前者写着"重要操作须经审批并经
审计记录…变更不走流程"，后者写着"没有告警通知，服务挂了靠客户投诉才知道"）。
那两题是**题目写错了**，不是系统答错了，已换成别的考点。
所以选题之后必须逐题看检索结果是不是"另一个正确答案"。

## 六、异常路径测试（`tests/test_edge_cases.py`，22 个用例）

下表已全部实现。**每条用例都不依赖 Ollama 是否在线**（一律用打桩代替真模型），
所以能稳定复现"模型抽风"这类现实中很难碰上的场景。

| 用例 | 期望 |
|---|---|
| 本地 Ollama 请求不被系统代理截走（`trust_env=False`） | 开了系统代理也能连上本机 11434 |
| 空问题被拒绝 | 提示"请输入问题"，不消耗模型 |
| Ollama 不可用时降级为条款检索 | 橙色降级标记 + 人话提示 + 给出启动方法 |
| 模型返回非法 JSON 时不崩溃 | 容错解析；再失败显示原文，不留白 |
| 从坏掉的 JSON 里只抢救 `answer` 字段 | 只认 `answer`；`""`、非 JSON、缺 `answer` 三种输入都返回 `None`，不误救 |
| 模型输出被截断时 | **不把原始 JSON 端给用户、不泄漏结构字段名、正文要救回来、引用必须兜底补上** |
| 截断输出里连 `answer` 都救不出来 | 改为列出检索到的条款，并在 `notes` 里说明"未能抢救出正文" |
| 模型返回空内容时兜底 | `mode` 变 `retrieval_only`，直接列出条款，引用不为空 |
| 知识库检索不到内容时拒答 | `mode=no_result`、`found=False`、正文含"未找到" |
| 超长问题（2 万字）被截断后再送给模型 | 只有截断点**之前**的内容进提示词 |
| 特殊字符与 XSS 字符不导致崩溃 | `"'<script>\` 等原样处理，不报错 |
| 模型编造条款号会被白名单剔除 | 库里不存在的条款号进不了引用卡片 |
| 未捕获异常有堆栈落盘且提示是人话 | 日志里有 `exc_info` 的完整堆栈，用户看到的是中文提示 |
| 导出不存在的会话返回 404 而不是崩溃 | 干净的 404 |
| 引用解析能处理各种写法 | 条款号、区间、多条并列都能解析 |
| 位置序号翻译不误伤正常中文 | "第一章"这类改写不破坏普通句子 |

**两个建测试时才暴露的缺陷（都写进用例注释里了）**

1. **降级引用补位必须放在 `answer_text` 兜底之后**。
   模型返回空内容时，引用补位的判断先于正文兜底执行，
   结果"正文救回来了、引用卡片却是空的"——**回答了却没有出处**，
   直接违反项目第一条硬性要求。
2. **超长问题的测试用了重复字符串**（`"同一句话" * 1200`），
   截断点之后的内容和开头完全一样，于是"截断点之后还在不在提示词里"永远为真，
   长期**假通过**。改成每段带不同编号（`第{i}点…`）才真正测到截断。
   同一个用例还依赖了 Ollama 在线——打桩后 12/12 变 16/16 稳定通过。

> 立下的规矩：**测试不得依赖外部服务是否在线**。
> 否则"测试挂了"和"模型没开"分不清，人就会开始忽略红色。

## 七、回归测试的纪律

**每次改动后必须做的四件事**：

1. 跑 `tests\check_syntax.py`（静态检查）
2. 跑 `tests\run_eval.py`，确认三项指标不低于红线
3. **改过 HTML/CSS/JS 就跑 `tests\test_frontend.py`**，确认页面在真浏览器里没坏
4. 打开浏览器亲手问 3 个问题（一个正常的、一个应该拒答的、一个应该追问的）

**没做这几件事的改动，不算完成。**

自动化能证明"没坏"，证明不了"好用"——第 5 层的人工验收不能省。

## 八、什么时候必须回滚

出现下面任何一种，**立即回滚到上一个可用状态**，不要试图硬修：

- 拒答正确率跌破 16/16
- 出现编造的条款号（引用卡片里的条款在知识库里查不到）
- 浏览器控制台报错且界面功能受影响
- 启动时间超过 60 秒
- 数据文件损坏

回滚方式见 06 号文档中每个步骤的"回滚"一栏。

## 十、第 6 层：模型评审与幻觉率（手工，不进 CI）

**为什么要有这一层。** 第 2 层只查「有没有追问」「库外法规有没有声明」，不判断答案本身好不好；
而 CI 不装 Ollama（铁律三），所以提示词改坏、换模型、JSON 兜底退化，**CI 全绿也发现不了**。
第 6 层让本地模型当评审（LLM-as-judge），逐题给三个维度打分并算幻觉率。
它是**手工层**：不进 CI、不进 `check_quality.py`、不进红线。

### 怎么跑

```powershell
.venv\Scripts\python.exe tools\llm_judge.py --limit 5   # 先跑 5 题做人工校准
.venv\Scripts\python.exe tools\llm_judge.py             # 全量 hit 题
.venv\Scripts\python.exe tools\llm_judge.py --self-test # 不联网，验证判卷/统计/报告流水线
.venv\Scripts\python.exe tools\llm_judge.py --probe     # 召回率校准：喂已知有/无幻觉的答案
```

`tests/run_eval.py` 在第二层（端到端）之后会自动接着跑这一节；发布前跑一次 `run_eval.py`
即可同时得到检索、端到端、幻觉率三份结果。

`run_eval.py` **没有单独的 `--judge` 开关**：不带 `--no-llm` 时自动跑，`--no-llm` 时跳过并在报告里
标「未执行」；退出码 `3` 覆盖「层 2 没跑」和「模型评审没跑/一道没判出」两种情况。
`--limit N` 同时限制端到端题数和评审题数，只适合冒烟：它会让「追问正确率」「库外法规声明率」
的分母变成 0，从而跌破红线——**别用 `--limit` 的结果代表全量质量**。

### 判什么

| 维度 | 5 分 | 3 分 | 1 分 |
|---|---|---|---|
| 忠于条款 | 每个事实陈述都能在引用条款原文找到依据 | 有少量概括但无矛盾 | 与原文矛盾，或引用条款不支持该陈述 |
| 不编造 | 没有引用条款和用户问题之外的具体事实 | 只有泛化表述 | 出现无依据的数字 / 时限 / 机构 / 价格 / 结论 |
| 回答切题 | 正面回应用户问题 | 只沾边 | 答非所问 |

**幻觉率 = 被判「出现无依据具体事实」的题数 ÷ 有回答的判卷题数。**
"无法判定"的题不进分母，单独报数；分母为 0 时报告写"无法判定"，不写 0%。
从 t28/t29 起回答正文由 `app/answer.py` 用条款原文拼装，模型不再写正文，
所以这一层的现实意义主要是**守住"不要让模型自由写正文"这条线**，同时暴露选错条款、风险标签乱标。

### 输出怎么读

- `tools/_judge_report.md`：结论（判卷数 / 幻觉率 / 均分 / 与人工一致率）、逐题表、低分题全文与理由、逐题回答。
- `tools/_judge_rows.json`：机器可读的逐题结果，供 `--agreement-only` 复用。
- 退出码：`0` = 已执行；`2` = **未执行**（Ollama 未就绪 / 没有可判的题）；`1` = 一道题都没判出来。
  **`2` 绝不能当成通过。**

### 召回率校准：`--probe`（2026-10-19 新增）

**它要回答的问题。** dev 集那 25 道 hit 题，答案本来就没有幻觉。拿它们算出的「幻觉率 0%」
只能证明 judge **不误报**，证明不了它**能报**——这就像问一条从不下雨的路有没有洪水。

`tests/judge_probe.json` 是人工写的校准集：答案一半注入条款里没有的具体事实
（编造时限 / 价格 / 机构 / 条款编号 / 条款内容 / 处罚后果），另一半逐句忠实于条款。
跑 `--probe` 会同时给出两个数字：

- **召回**：有幻觉的条目里，judge 报出了几条。低召回 = judge 是个只会说「没问题」的橡皮图章。
- **误报**：干净条目里，judge 冤枉了几条。

两个数必须一起看：只报召回，判得越严越好看；只报误报，一个永远说「没问题」的 judge 最完美。
校准集不进 CI（要 Ollama），也不进红线——它的产出是「这个 judge 能不能用」的判断依据。

### 事实回查与精确率（确定性核验）

judge 除了打分，还会列出它认为「条款里没有」的具体事实。这些事实**不能直接采信**：
工作流会拿**未经截断的完整条款正文**把每条事实回查一遍，给出三种结论：

| 结论 | 含义 |
|---|---|
| `unsupported` | 关键词在条款正文里一个都找不到 → judge 判对了 |
| `supported` | 其实就在条款正文里 → **judge 判错**（幻觉率里有误报） |
| `ambiguous` | 只有部分词对上，无法断言 → 不计入精确率，单独报数 |

报告里的「judge 事实精确率」= `unsupported ÷ (unsupported + supported)`。
中文按 2 字滑窗切词再比对，不按整句——「30 日内完成备案」和「30 天内完成备案」
字面不同、语义相同，整句匹配会把 judge 判错的情况漏掉。

还有一条要注意：提示词里 judge 最多看到 6 条条款、每条 900 字。**超出的部分它本来就没看见**，
那些位置上的「无依据」是我们的截断造成的，不是它判错。报告会单独列出这类题目
（`⚠️ 提示词截断`），回查用的是完整正文，所以能区分开。

### 确定性判据：能查的不要问模型（2026-10-21 新增）

`tools/llm_judge.py::deterministic_claims()` 不经模型，直接判两类「无依据具体事实」：

1. **数字类**：答案正文里的数字（时限、价格、次数、编号里的数字），在被引条款正文里找不到；
2. **编号类**：答案里提到的条款编号，知识库里根本不存在。

只扫正文行——以 `**条款号 标题**` 开头的行是工具自己拼的标题，跳过；
扫描前先把编号整体剔掉，否则标题里的 `8.1.4.1` 会被当成「条款里没有的数字」。

为什么非加不可：实测第一版 judge 对 12 条编造答案的召回是 **0**（见上一节）。
而「30 日内备案」里的 30 在条款里没有——这件事查一下就知道，不该送去问 7B 模型。

判定的结果并进同一个 `hallucinated` 字段，但内部保留 `model_flagged`（模型层）与
`deterministic`（确定性层）两个来源，`--probe` 报告里按层统计
（`layer_model_only` / `layer_deterministic` / `layer_both`）。
**分层是必须的**：只看总数，就无法判断该往哪一层投入。

#### 比对基准必须是「正文里真正引用的条款」

`/api/chat` 返回的 `citations` 只有**模型点名的那几条**，而答案正文渲染的是本次检索到的
**全部条款**——实测一条正文里有 6 个条款块、`citations` 只有 2 条。
拿 2 条当基准去查数字，另外 4 条里的数字全会变成「条款里找不到」，
那是基准错了，不是答案编造。

所以 `citations_from_answer(answer, citations)` 会从正文的 `**编号 标题**` 头行里
把缺的条款补齐再交给 judge。做召回率校准时，这一条比调阈值重要得多。

另外两类**服务端自己写的行**也要跳过，否则同样会冤枉答案：

| 行 | 里面的数字来自 | 为什么不能算编造 |
|---|---|---|
| 开场白 / 概述 / 免责收尾 | 固定文案 | 服务端常量 |
| 库外法规说明 | `GB/T 22239-2019`、`OWASP Top 10 2021` | 标准编号，本来就不在条款正文里 |
| 条款块标题 `**8.1.4.1 标题**` | 知识库字段 | 不是模型写的 |

还有一类纯技术坑：`MD5`、`SHA256`、`TLS1.2` 里的数字会被正则当成「编号里的数字」。
数字前不能紧邻 ASCII 字母，编号至少三段（两段的 `等保2.0` 不是条款编号）。

### 来源指纹

报告头部固定记录：**代码版本（git commit）/ 提示词版本 / 知识库条数与签名 / 评审模型**。

为什么必须有：没有指纹的百分比不可比。换了提示词、换过知识库、换了模型之后的
「幻觉率 0%」和上一次不是同一个 0%。有了指纹，跨版本比较才有意义；没有指纹，
它只能当一次性快照，不能写进任何趋势或结论里。

### judge 自己也要校准

judge 也是模型。至少人工标注 5 条：新建 `tools/_judge_human.json`（格式见报告末尾），
填 `hallucination` / `faithful` / `relevant`，然后运行：

```powershell
.venv\Scripts\python.exe tools\llm_judge.py --agreement-only
```

一致率低于 80% 就说明这个 judge 不可用，报告里要如实写，不能拿它当质量证据。
**样本里没有幻觉时，一致率只能证明"没有误报"，不能证明"能抓到幻觉"**；
抓幻觉的能力由 `--probe` 的真实注入样本 + `--self-test` 的合成样本验证。

### 当前实测：judge 曾经是个橡皮图章（2026-10-21）

环境：`qwen2.5:7b-instruct`，本机 Ollama。

**召回率校准集（`--probe`，20 条人工答案，12 条注入条款里没有的事实）**

| 阶段 | 召回 | 误报 |
|---|---|---|
| 第一版评分标准 | **0/12（0%）** | 0/8 |
| 改评分标准（先抄事实再逐条对照） | 3/8（38%，只跑前 8 条） | — |
| 只靠确定性判据 | 9/12（75%） | **0/8** |
| **最终（确定性 + 回查过滤后的模型层）** | **9/12（75%）** | **0/8** |

第一版把 12 条明显编造的答案**一条都没报**：每条都返回 `faithful=5 / no_fabrication=5 /
relevant=5`、`unsupported_facts=[]`，理由统一是「有条款依据、切题」。
也就是说，**在加确定性判据之前，「幻觉率 0%」这个数字毫无信息量**。

**真实答案（25 道 hit 题，产品实际输出）**

- 幻觉率 **0/25**，与人工标注一致率 **5/5（100%）**。
- 分层：确定性层 0 条、模型层 0 条——两边都没有误判。

**这两个 0% 要分开理解，否则又是自欺：**

真实答案是 0/25，很大程度上是**结构决定的**：正文 100% 由服务端拼装（开场 / 概述 /
条款块 / 风险标签 / 收尾），模型只能输出 `found / clauses / risk_tags / need_clarification`，
**正文里没有任何位置可以放模型写的话**。所以「产品幻觉率 0%」证明的是架构成立，
不是 judge 英明。

judge 值不值得信任，看的是校准集：**12 条注入幻觉里它能抓到 9 条，8 条干净答案一条都没冤枉**。
漏掉的 3 条（`p03`、`p08` 编造机构名，`p12` 编造处罚后果）都是**没有数字、没有编号可查**的纯语义编造。

> 中间踩过的坑（都记在这里，因为下次还会踩）：
> 第一次跑全量真实答案得出「幻觉率 14/25（56%）」，是**测量错误**，不是产品错误——
> 比对基准用错了（`citations` 只有模型点名的 2 条，正文却渲染了 6 个条款块），
> 加上 judge 报的「无依据事实」没有回查过滤（3 条是服务端自己写的行、9 条是条款正文原文）。
> 修完基准与过滤是 0/25。**先怀疑测量，再怀疑产品。**
