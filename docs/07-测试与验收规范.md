# 07 · 测试与验收规范

> 这个项目最怕的不是崩溃，而是**"测试通过但答得不对"**。
> 所以测试的重点不是"代码跑不跑得起来"，而是"答得准不准"。

---

## 一、测试分六层

| 层 | 测什么 | 在哪 | 什么时候跑 |
|---|---|---|---|
| **第0层 · 静态检查** | Python/JS 语法、JSON 格式、JS 引用的元素 ID 是否存在、SVG 图标名是否有定义、`.bat` 是否纯 ASCII、独立脚本打印非 ASCII 时有没有把 stdout 切成 UTF-8 | `tests/check_syntax.py` | **每次改完代码，跑评测之前** |
| **第1层 · 检索与判定质量** | 该命中的有没有命中、无关问题会不会误答、库外法规有没有识别、适用性判定有没有拦住、⚠️ 有没有误标 | `tests/run_eval.py --no-llm` | **每次改动后必跑（秒级）** |
| **第2层 · 端到端问答** | 模型真的追问了吗、库外法规声明真的写进回答正文了吗、有没有转述条文 | `tests/run_eval.py`（默认两层都跑） | 改了提示词或回答逻辑后 |
| **第3层 · 异常路径** | 断网、模型挂掉、空知识库会不会白屏 | `tests/test_edge_cases.py` | 改了错误处理或接口后 |
| **第3层 · 纯逻辑单测** | 范围判定、风险标注、口语归一化、流式解析、Word 导出、导入与撤销 | `tests/test_scope.py`、`tests/test_guard.py`、`tests/test_normalize.py`、`tests/test_streaming.py`、`tests/test_export.py`、`tests/test_revert.py` | 改了对应模块后 |
| **第4层 · 界面（真浏览器）** | 页面在真 Chrome 里能不能用：JS 有没有报错、axe-core 无障碍扫描、键盘能不能操作、字体加载、手机宽度有没有溢出、抽屉导航能不能开合 | `tests/test_frontend.py` | 改了 HTML/CSS/JS 之后 |
| **第5层 · 人工验收** | 浏览器里亲手用一遍，是不是真的好用 | 手动 | 每次交付前 |

**第3层和第4层的套件都不依赖 Ollama**，所以它们在任何时候都能跑。
这条纪律是踩过坑才立的：曾经有个"超长问题"的用例同时依赖 Ollama 在线，
而且断言写成了永远为真，长期"假通过"。

### 第4层的由来（语法正确 ≠ 页面能用）

第0层解决了"JS 语法错误"，但语法正确的代码仍然可以在浏览器里崩掉：
元素 ID 对不上、DOM 结构假设错了、事件绑在根本不存在的节点上。
更隐蔽的是 CSS——`.empty-state` 的样式一改，
"HTML 里写了一份空状态、JS 又生成一份"这个重复 bug 才暴露出来。

所以第4层真的拉起一个临时端口的服务、用本机 Chrome 把页面渲染出来再断言。
见 `tests/test_frontend.py`（17 个用例）与 `tests/frontend_probe.js`（只采事实，判定在 Python 里）。

**它的额外前提**：本机要装 Node.js 和 Chrome。缺任何一个会直接判失败并说明缺什么，
**不静默跳过**——静默跳过等于给自己发一张假的通行证。
`tools/cdp_eval.js` 用 Node 自带的 `WebSocket` 直接讲 CDP 协议，
**没有引入 puppeteer / playwright**：这个项目要求零运行时依赖且能离线跑，
测试基础设施不该成为例外。

### 第0层的由来（别跳过它）

有一次 `web/js/kb.js` 里写成了 `dengbao_2.0: '等保2.0'`——
`dengbao_2.0` 不是合法的 JS 变量名（会被解析成 `dengbao_2` 后面跟个 `.0`），
**整个知识库页面在浏览器里会直接失效**。

而当时的验证只检查了"这个文件能返回 HTTP 200"，完全没发现。

所以现在每次改完代码，先跑：

```bat
.venv\Scripts\python.exe tests\check_syntax.py
```

它会检查：Python 语法、`node --check` 校验 JS（`web/`、`tools/`、`tests/` 三个目录）、
JSON 格式、**JS 里引用的每个元素 ID 是否真的存在于 HTML 中**、
以及**JS/HTML 里用到的每个 SVG 图标名在雪碧图里有没有定义**
——这两类错误都只在浏览器里暴露，而且图标名写错时浏览器**不报任何错**，只是画一片空白。

还有两条是跟 Windows 的字符编码有关的，都栽过跟头：

- `check_bat_ascii()`：`.bat` 必须是纯 ASCII。cmd.exe 按**当前控制台代码页**逐字节读批处理
  文件，文件里有中文而代码页不匹配时命令会被撕碎，表现是**双击脚本什么都不发生**。
- `check_console_encoding()`：**不 `import app` 的独立脚本**如果会打印非 ASCII，必须自己把
  `sys.stdout` 切成 UTF-8。原因是 Windows 上标准输出被重定向（管道、写文件、CI 抓取）时，
  Python 按控制台代码页编码：开发机是 GBK，中文编得出来，所以这个缺陷在本地**永远看不见**；
  GitHub Actions 的 windows runner 是 cp1252，打印中文直接 `UnicodeEncodeError` 崩掉进程。
  第一次跑 CI 就是这么挂的（`tests/check_syntax.py` 自己中招）。
  `import app.*` 的脚本由 `app/console.py` 自动修好，所以规则只约束独立脚本。

> 本地想复现 cp1252 环境：`$env:PYTHONIOENCODING = "cp1252"` 再跑一遍脚本。


**为什么第1层最重要**：它是唯一能**自动、快速、客观**反映"答得准不准"的手段。
改任何东西跑一遍，指标掉了立刻就知道。

## 二、指标红线

| 指标 | 红线 | 含义 | 当前值 |
|---|---|---|---|
| **拒答正确率** | **必须 5/5** | 无关问题必须拒答 | 5/5 |
| **库外法规识别率** | **必须 6/6** | 点名了知识库里没有的法规时必须识别出来 | 6/6 |
| **适用性判定拦截率** | **必须 4/4** | "这条对我适用吗"这类问题必须拒绝硬答 | 4/4 |
| 检索召回率 | ≥ 27/29 | 该命中的条款出现在前 6 条里 | 29/29 |
| ⚠️ 风险标注率 | ≥ 8/9 | 该标的风险标上了 | 9/9 |
| ⚠️ 误标率 | **误标 ≤ 0 处** | 不该标的标签一个都不能标 | 0/2 |
| 单次回答耗时 | ≤ 10 秒 | 端到端 | 1.3 ~ 4.3 秒 |
| 引用真实率 | 100% | 引用卡片里的条款必须都真实存在 | 100%（服务端强制） |

### 三条一票否决项

**宁可答"找不到"，也绝不能编造条款、更不能替用户做适用性判定。**

- **拒答正确率**跌破 5/5
- **库外法规识别率**跌破 6/6
- **适用性判定拦截率**跌破 4/4

上面任何一条掉了，**不管别的指标多好看，都必须回滚**。

### 为什么数量本身也要卡（`EXPECTED_COUNTS`）

只看"通过数 / 红线数"有个致命盲区：**如果把题库删掉一半，通过数会跟着缩水，
红线却还是显示"通过"**。所以 `app/quality.py` 里同时卡了两样东西——
每一类的题目数量下限，和通过数。加题时两处都要改。

红线定义在 `app/quality.py` 的 `RED_LINES` 与 `EXPECTED_COUNTS`，
**改这里之前先改本文件**。

## 三、怎么跑测试

```bat
rem 第0层：静态检查（最先跑，最快）
.venv\Scripts\python.exe tests\check_syntax.py

rem 第1层：检索与判定质量（快，约 5 秒，不需要 Ollama）
.venv\Scripts\python.exe tests\run_eval.py --no-llm

rem 第1+2层：连大模型端到端（慢，约几分钟；Ollama 没开会自动跳过第二层）
.venv\Scripts\python.exe tests\run_eval.py

rem 第2层只想跑前几题（调试用）
.venv\Scripts\python.exe tests\run_eval.py --limit 6

rem 第3层：异常路径（16 个用例）
.venv\Scripts\python.exe tests\test_edge_cases.py

rem 第3层：范围判定（13 个用例，覆盖范围/库外法规/适用性判定，不依赖 Ollama）
.venv\Scripts\python.exe tests\test_scope.py

rem 第3层：风险标注（11 个用例，含误标回归）
.venv\Scripts\python.exe tests\test_guard.py

rem 第3层：口语归一化与分词（10 个用例）
.venv\Scripts\python.exe tests\test_normalize.py

rem 第3层：导入与撤销（10 个用例，用临时数据库，不动真实数据）
.venv\Scripts\python.exe tests\test_revert.py

rem 第3层：流式输出（12 个用例，纯函数，不依赖 Ollama）
.venv\Scripts\python.exe tests\test_streaming.py

rem 第3层：Word 导出（10 个用例）
.venv\Scripts\python.exe tests\test_export.py

rem 第4层：界面（17 个用例；需要本机有 Node.js 和 Chrome，约 40 秒）
.venv\Scripts\python.exe tests\test_frontend.py

rem 只想快速判断达标不达标（退出码 1 = 跌破红线，可接自动化）
.venv\Scripts\python.exe tools\check_quality.py --quiet
```

**全部套件的退出码都必须是 0。** 一共 **9 个套件 / 99 个用例**。报告会写到 `tests/eval_report.md`。

`tests/test_frontend.py` 是最慢的一个（要真开浏览器），所以放在最后跑。
它跟别的套件一样**不依赖 Ollama**，但依赖 Node.js 和 Chrome；
两者缺一时它会立刻失败并打印缺哪个，不会假装通过。
它用的是**数据库的临时副本**，跑测试不会动你的历史记录。

> **注意**：改过 `app/normalize.py` 的 `tokenize()` 或 `COLLOQUIAL_MAP` 之后，
> **必须重建索引**——`FTS5` 里存的是分词后的结果，不重建的话检索还在用旧词表：
>
> ```bat
> .venv\Scripts\python.exe tools\build_index.py
> ```

### 全新检出（CI 和新人第一次跑）

干净 clone 下来没有 `data/app.db`，先跑一次这个把知识库建起来：

```bat
.venv\Scripts\python.exe tools\build_index.py
```

它发现库是空的会自动从 `data/seed` 导入 283 条种子条款，并建好全文索引与语义向量
（实测 3.5 秒，其中大部分是加载语义模型）。**没有这一步，需要知识库的套件全部会失败。**

### CI（`.github/workflows/ci.yml`）

每次 push 到 `main` 和每个 PR 都自动跑：

| 作业 | 平台 | 内容 |
|---|---|---|
| 后端套件 | `ubuntu-latest` + **`windows-latest`** | 8 个套件 + `run_eval.py --no-llm` |
| 界面回归 | `ubuntu-latest` | `test_frontend.py`（真 Chrome + axe-core） |

几个刻意的选择：

- **后端跑两个平台**。Windows 才是这个项目的主要目标平台（用户双击 `.bat` 启动），
  但 ubuntu 快得多——两个都跑，信号最全。
- **界面套件只跑 ubuntu**：`tools/cdp_eval.js` 的 `findChrome()` 认 Linux/macOS/Windows
  三种路径，界面行为本身与平台无关。
- **语义模型用 `actions/cache` 缓存 `data/models`**。CI 里唯一需要联网的地方就是
  fastembed 下载 `BAAI/bge-small-zh-v1.5`（约 95 MB），缓存命中就不下了。
- **设 `HF_MIRROR=https://huggingface.co`**：开发机在国内默认走 `hf-mirror.com`
  （`app/config.py` 的 `setdefault`），runner 上官方源更快更稳。
- **不跑 `run_eval.py` 的端到端那一档**（需要 Ollama）。CI 里没有大模型，
  这正是铁律三要保证的：**测试不许依赖外部服务是否在线**。

### 输出怎么读

```
检索召回率   29/29    ← 该命中的都命中了
拒答正确率   5/5      ← 死线，不能掉
库外法规识别率 6/6     ← 死线：点名库外法规必须识别出来
适用性判定拦截率 4/4   ← 死线：不能替用户做适用性判定
⚠️ 误标率    0/2      ← 误标 ≤ 0 处
```

逐题输出里带 `XX` 的行就是失败的，下面会跟一行说明为什么不通过。

## 四、评测集（`tests/eval_questions.json`）

30 道题，分三类：

| 类别 | 题数 | 用途 |
|---|---|---|
| 真实合规问题（期望命中） | 20 | 测召回率 |
| 完全无关问题（期望拒答） | 5 | 测拒答能力（**最关键**） |
| 信息不足的问题（期望追问） | 2 | 测追问逻辑 |
| 其他（按编号查询、等保分级等） | 3 | 测特殊情况 |

每道题的字段：

```json
{
  "id": "q01",
  "question": "我们公司十几个人都用同一个管理员账号登录进销存系统，这样有问题吗？",
  "expect": "hit",
  "must_include_any": ["8.1.4.1", "8.1.4.29", "8.2.3"],
  "risk_expect": ["access_control"],
  "note": "账号共享 → 身份鉴别/访问控制"
}
```

| 字段 | 说明 |
|---|---|
| `expect` | `hit` 期望命中；`reject` 期望拒答；`out_of_kb` 期望识别出"点名了库外法规"；`undeterminable` 期望拒绝做适用性判定 |
| `must_include_any` | top-6 里**至少出现一个**这些编号（支持前缀匹配）。留空表示只要求"命中" |
| `risk_expect` | 期望的 ⚠️ 标签。**只填三类高风险，其他标签不参与评分** |
| `risk_forbid` | **不许**出现的 ⚠️ 标签（误标回归用）。判定方式是"假设模型见谁都标"，看这三个标签会不会被标出来 |
| `out_of_kb_expect` | `expect: "out_of_kb"` 时，期望识别出的法规名（子串匹配） |
| `clarify_expect` | 期望先追问 |

### 四类 expect 分别防的是什么

| 类型 | 防的缺陷 | 例子 |
|---|---|---|
| `hit` | 该答的答不出来 | "十几个人共用一个管理员账号" |
| `reject` | 无关问题硬答、编造条款 | "今天北京的天气怎么样" |
| `out_of_kb` | **用户点名库外的法规时凭记忆编造条文** | "《个人信息保护法》第 13 条怎么规定的？" |
| `undeterminable` | **替用户做适用性判定，罗列一份"不适用条款清单"** | "列出等保三级里所有不适用的条款" |

后两类是 2026-10-08 审计新加的。加它们的原因值得记住：
这两类问题**检索分数都很高**（0.53~0.97），阈值闸门根本拦不住，
而原来的评测集里一道这样的题都没有——所以缺陷存在了很久却一直显示"全部达标"。

### 加测试题的规矩

**每修一个 bug，都要把它变成一道测试题。** 否则下次会再犯。

加题时注意：

- `must_include_any` 不要写太窄。如果一个问题的合理答案有好几个条款，
  就都列进去（用前缀匹配）。**测试写太窄会造成假失败**——
  实际召回的条款是对的，只是因为不在你列的清单里就判失败。
- 用 `expect: "reject"` 的题要真的有把握它是无关的，别把模糊的合规问题放进去。
- **加题之后要同步改 `app/quality.py` 的 `EXPECTED_COUNTS` 和 `RED_LINES`**，
  否则新题不参与红线判定，等于没加。
- `risk_forbid` 只写"真的完全不该出现"的标签。如果被检索到的条款本身
  就带这个标签（比如 `8.1.4.26`「个人信息保护」的 `risk_tags` 含 `personal_info`），
  那么模型真引用了它、标出 `personal_info` 是**正确行为**，不该写成禁止项。

### 留出集：防止"照着测试集调参"（`tests/eval_holdout.json`）

**先说问题**。上面这 44 题（下称 dev 集）是这个项目唯一的评测依据，而阈值 0.40、
关键词/语义权重 0.5:0.5、`COLLOQUIAL_MAP` 的每一批词，全都是**照着它调**出来的。
于是它衡量的已经不再是"系统能不能用"，而是"系统能不能通过这一套题"。
dev 集 6 项指标全绿，**并不能推出**换一批没人调过的题也全绿。

**再说解法**。新增留出集 `tests/eval_holdout.json`（31 题），三条纪律：

| 纪律 | 怎么落地 |
|---|---|
| 考不同的东西 | 条款全部取自 dev 集从未引用过的那一批（283 条里 dev 覆盖 203 条、剩 80 条，用 `tools/eval_coverage.py` 复算）；题干与条款模式都与 dev 集零重叠 |
| 不许偷偷改 | 指纹锁 `tests/eval_holdout.lock.json` 存 sha256；改动留出集会让 `tests/test_eval_discipline.py` 失败，逼你先想清楚"我改的是尺子，还是因为量出来的数不好看" |
| 基准只能升不能降 | 每类的最低通过数记在锁里。变差立刻失败；变好也不会自动涨及格线，要显式 `--raise-baseline` |

```bat
rem 检查（本地与 CI 都跑这个）
.venv\Scripts\python.exe tests\test_eval_discipline.py

rem 有意修改留出集之后，刷新指纹与题数（不动基准）
.venv\Scripts\python.exe tests\test_eval_discipline.py --update-lock

rem 确认当前成绩可作为新基准（拒绝下调，除非 --force）
.venv\Scripts\python.exe tests\test_eval_discipline.py --raise-baseline
```

**怎么读分数**：留出集不看"通过/不通过"，看**与 dev 集的差距**。
dev 100% 而留出 60% 说明在过拟合；两者接近才说明真的学到了通用规律。

**首次建立起留出集时的实测结果**（2026-10-10）：

| 分类 | dev 集 | 留出集 |
|---|---|---|
| 该命中 | 29/29 | 22/22 |
| 该拒答 | 5/5 | **0/3** |
| 库外法规识别 | 6/6 | 3/3 |
| 适用性判定拦截 | 4/4 | 3/3 |
| ⚠️ 误标 | 0 处 | 0 处 |

**唯一的缺口就是拒答，而且是同一类问题的两种难度**：dev 集的 5 道拒答题是
"今天天气怎么样""推荐几部电影"这种明显无关的，分数天然很低；留出集的 3 道是
"员工的加班费怎么算""纸质合同要保存多少年""产品出口欧盟要不要做 CE 认证"——
**长得像合规问题，但不属于网络安全合规**，检索分数 0.470~0.548，直接越过了 0.40 阈值，
被判成"库里有答案"。这说明 **5/5 的拒答成绩并不代表拒答能力够用**。

> **不要为了补这个缺口去调阈值或往 `scope.OUT_OF_KB_REGULATIONS` 里加法规**——
> 那等于照着留出集调参，尺子当场就废了。正确做法是往 **dev 集**里补几道同类的
> "难拒答"题，在 dev 上把方案调好，再回来看留出集涨没涨。
> 这条规则写在 `tests/eval_holdout.lock.json` 的 `known_gaps` 里，改之前先读它。

**一条选题教训**："未覆盖的条款"不等于"未覆盖的考点"。初次给留出集选题时有两道题
期望的是 NIST 的 `ID.RA-07`（变更管理）和 `DE.CM-01`（网络监测），结果系统检索到的是
等保 `8.1.5.2` 与 `8.2.5.20`，**正文完整回答了问题**（前者写着"重要操作须经审批并经
审计记录…变更不走流程"，后者写着"没有告警通知，服务挂了靠客户投诉才知道"）。
那两题是**题目写错了**，不是系统答错了，已换成别的考点。
所以选题之后必须逐题看检索结果是不是"另一个正确答案"。

## 六、异常路径测试（`tests/test_edge_cases.py`，16 个用例）

下表已全部实现。**每条用例都不依赖 Ollama 是否在线**（一律用打桩代替真模型），
所以能稳定复现"模型抽风"这类现实中很难碰上的场景。

| 用例 | 期望 |
|---|---|
| 本地 Ollama 请求不被系统代理截走（`trust_env=False`） | 开了系统代理也能连上本机 11434 |
| 空问题被拒绝 | 提示"请输入问题"，不消耗模型 |
| Ollama 不可用时降级为条款检索 | 橙色降级标记 + 人话提示 + 给出启动方法 |
| 模型返回非法 JSON 时不崩溃 | 容错解析；再失败显示原文，不留白 |
| 从坏掉的 JSON 里只抢救 `answer` 字段 | 只认 `answer`；`""`、非 JSON、缺 `answer` 三种输入都返回 `None`，不误救 |
| 模型输出被截断时 | **不把原始 JSON 端给用户、不泄漏结构字段名、正文要救回来、引用必须兜底补上** |
| 截断输出里连 `answer` 都救不出来 | 改为列出检索到的条款，并在 `notes` 里说明"未能抢救出正文" |
| 模型返回空内容时兜底 | `mode` 变 `retrieval_only`，直接列出条款，引用不为空 |
| 知识库检索不到内容时拒答 | `mode=no_result`、`found=False`、正文含"未找到" |
| 超长问题（2 万字）被截断后再送给模型 | 只有截断点**之前**的内容进提示词 |
| 特殊字符与 XSS 字符不导致崩溃 | `"'<script>\` 等原样处理，不报错 |
| 模型编造条款号会被白名单剔除 | 库里不存在的条款号进不了引用卡片 |
| 未捕获异常有堆栈落盘且提示是人话 | 日志里有 `exc_info` 的完整堆栈，用户看到的是中文提示 |
| 导出不存在的会话返回 404 而不是崩溃 | 干净的 404 |
| 引用解析能处理各种写法 | 条款号、区间、多条并列都能解析 |
| 位置序号翻译不误伤正常中文 | "第一章"这类改写不破坏普通句子 |

**两个建测试时才暴露的缺陷（都写进用例注释里了）**

1. **降级引用补位必须放在 `answer_text` 兜底之后**。
   模型返回空内容时，引用补位的判断先于正文兜底执行，
   结果"正文救回来了、引用卡片却是空的"——**回答了却没有出处**，
   直接违反项目第一条硬性要求。
2. **超长问题的测试用了重复字符串**（`"同一句话" * 1200`），
   截断点之后的内容和开头完全一样，于是"截断点之后还在不在提示词里"永远为真，
   长期**假通过**。改成每段带不同编号（`第{i}点…`）才真正测到截断。
   同一个用例还依赖了 Ollama 在线——打桩后 12/12 变 16/16 稳定通过。

> 立下的规矩：**测试不得依赖外部服务是否在线**。
> 否则"测试挂了"和"模型没开"分不清，人就会开始忽略红色。

## 七、回归测试的纪律

**每次改动后必须做的四件事**：

1. 跑 `tests\check_syntax.py`（静态检查）
2. 跑 `tests\run_eval.py`，确认三项指标不低于红线
3. **改过 HTML/CSS/JS 就跑 `tests\test_frontend.py`**，确认页面在真浏览器里没坏
4. 打开浏览器亲手问 3 个问题（一个正常的、一个应该拒答的、一个应该追问的）

**没做这几件事的改动，不算完成。**

自动化能证明"没坏"，证明不了"好用"——第 5 层的人工验收不能省。

---

## 八、什么时候必须回滚

出现下面任何一种，**立即回滚到上一个可用状态**，不要试图硬修：

- 拒答正确率跌破 5/5
- 出现编造的条款号（引用卡片里的条款在知识库里查不到）
- 浏览器控制台报错且界面功能受影响
- 启动时间超过 60 秒
- 数据文件损坏

回滚方式见 06 号文档中每个步骤的"回滚"一栏。
