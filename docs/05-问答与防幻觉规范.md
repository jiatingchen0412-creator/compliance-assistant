# 05 · 问答与防幻觉规范

> 这个软件的**生命线**是"不编造条款号"。这份文档规定它该怎么回答、怎么引用、
> 什么时候该拒答、什么时候该追问。**改提示词之前必须看这里。**

---

## 一、回答的六条规则

这六条对应 `app/prompt.py` 里的 `SYSTEM_PROMPT`，是给大模型的硬性约束。
**编号与提示词正文里的【规则N】一一对应，改一边就要改另一边。**

> **总原则：提示词只是"请它别这么干"，代码才是"让它干不成"。**
> 凡是"答错了会严重误导用户"的行为（编造条文、替用户做适用性判定、
> 把笼统问题当成已知情况回答），必须由服务端代码拍板——
> 因为只有代码里的保证才能被**离线测试**证明（`tests/test_scope.py`、
> `tests/test_guard.py` 不需要 Ollama 就能跑）。

### 规则1 · 引用只能来自【可用条款】

- 回答只能引用本次检索到的条款编号
- 引用时必须写**条款编号本身**（`8.1.4.1`、`PR.AA-01`、`A01:2021`）
- **绝对不许**写成"条款1""第1条"这种序号（序号只是给模型看的，用户看不懂）
- 不许编造条款号，不许编造条款内容

### 规则2 · 照着【可用条款】回答，不许自由发挥

判断标准只有一个：**【可用条款】里有没有和用户问题相关的条款**。

| 情况 | `found` | 回答怎么写 |
|---|---|---|
| 有相关条款（哪怕不完全对应他的具体情况） | `true` | 必须引用这些条款、说明要求什么。**不许说"未找到"** |
| 完全无关（用户问天气、电影） | `false` | 明确说"知识库中未找到…"，建议咨询专业安全顾问 |

> **这条规则被"矫枉过正"过一次，教训值得留着**：
> 为了修"明明检索到了却说找不到"，旧版规则2 写成过
> "只要有一点点相关就一律 found=true，**绝对不许**说知识库中未找到"。
> 结果连"用户问的是知识库里根本没有的法规"这种真正该拒答的情形
> 也被一并封死了——于是模型开始凭记忆编造《个人信息保护法》的条文。
> 现在的写法把两件事分开：**"库里有没有"只看【可用条款】**，
> 而**"能不能转述库外法规的内容"是另一回事**（见规则2b）。

### 规则2b · 库外法规只说明"未收录"，绝不转述它的内容

用户点名了知识库没收录的法规（《个人信息保护法》、GDPR、ISO 27001…）时：

- 只能说"本工具未收录这部法规"并建议查阅官方文本或咨询顾问
- **绝不转述它的条文内容、条号含义、适用范围**——哪怕模型"记得"
- 服务端还会再兜一道：`guard.strip_out_of_kb_claims()` 会按句删掉
  转述库外法规的句子（见第二节）

> **为什么必须有这条**：这类编造最难被发现——模型会一边编《个人信息保护法》
> 第 13 条的内容，一边挂上**真实存在**的等保引用编号，
> 用户根本分辨不出哪句有据可查。实测 3/3 稳定复现，
> 而且编出来的内容本身就是错的（把第 5/6 条的原则安到了第 13 条上）。

### 规则3 · 高风险必须标注

涉及数据加密 / 访问控制 / 个人信息保护三类主题时，`risk_tags` 必须填对应值，
并在正文里用 ⚠️ 开头的句子单独说出来。

### 规则4 · 信息不足才追问，追问不等于拒答

**`found` 和 `need_clarification` 是完全独立的两件事**：

```
found              = 知识库里有没有相关条款
need_clarification = 用户描述够不够具体
```

| 情况 | 判断 | 该怎么做 |
|---|---|---|
| **A. 已描述具体情形**<br>（"共用管理员账号""手机号没加密""离职权限没回收"） | `need_clarification = false` | 直接给：结论 + 条款依据 + 2-4 条自查动作 |
| **B. 只说了很笼统的话**<br>（"我们系统安全吗""合规难不难"） | `need_clarification = true` | 仍然 `found = true`，仍然引用条款并说明大致管什么，**然后再问** 1-3 个具体问题 |

**任何时候都不许把"我需要更多信息"表达成"知识库里没有"。**

> **实测 7B 模型经常漏做这条**：问"我们的数据安全吗？""要不要做等保？"
> 它直接给一段泛泛的结论，一个反问都没有。而这段结论读起来是
> "已经看过你的情况了"的口吻，用户会当真。
> 所以服务端加了确定性兜底：`scope.needs_clarification()`
> 在"问题很短 + 命中了笼统问法 + 完全没提具体情形"三条同时成立时，
> 强制补上追问，并在回答最前面加一句"您说的情况还比较笼统"。
> 判定刻意**写得窄**——误判（用户问了具体问题却被反问一圈）比漏判更烦人。
> `tests/test_scope.py` 里既有 4 道"必须追问"的题，也有 8 道"必须不追问"的对照。

### 规则5 · 不替用户做适用性判定

"哪些条款不适用""这条对我们适用吗""哪些要求没覆盖"这类问题，
必须结合用户系统的**定级结果、业务范围、部署模式**逐条比对才能判断。
在用户没有提供这些信息时：

- 不要罗列条款编号当作"不适用条款清单"——这是最容易出错、也最误导人的做法
- 应说明"这无法在不了解您系统具体情况的前提下判定"，并建议做正式适用性分析

> 这类问题**在 `chat.py` 里根本不调模型**：命中后直接返回服务端模板
> （`scope.needs_context_answer`）。理由见 `app/scope.py` 的模块注释——
> 让模型去编一份条款清单只会害人。

## 二、服务端强制修正（比提示词更可靠）

提示词是"请求"，服务端校验才是"强制"。以下是代码层面的硬规则：

| 规则 | 位置 | 说明 |
|---|---|---|
| **阈值拒答** | `retrieval.py` | 最高分 < `RETRIEVAL_MIN_SCORE`（0.40）→ 直接返回"未找到"，**根本不调大模型** |
| **库外法规识别** | `scope.detect_out_of_kb` | 在**阈值闸门之前**判定；命中后服务端强制拼一段"该法规未收录"说明在最前面，模型删不掉 |
| **清理库外法规转述** | `guard.strip_out_of_kb_claims` | 按句删掉转述库外法规内容的句子。**顺序关键：先清模型的、再拼服务端的**，反了会误伤服务端那段说明（它自己就带法规名） |
| **适用性判定不调模型** | `routers/chat.py` | 命中 `scope.needs_system_context` → 直接用服务端模板回答，`mode="needs_context"` |
| **缺信息时强制追问** | `scope.needs_clarification` | 服务端单向补位：模型说要追问就尊重它，模型漏了而规则有把握时才补上 |
| **`found` 归属** | `routers/chat.py` | 服务端不替模型下结论：模型说找到了才回填引用；模型说"没找到"就按没找到处理（`model_found = bool(data.get("found", True))`），**不再把"我没找到"改写成"已找到"** |
| **剔除非法引用** | `guard.validate_citations` | 模型给的编号逐个比对检索结果，对不上的剔除并记入技术详情 |
| **正文编号扫描** | `guard.detect_hallucinated_ids` | 正文里出现不在检索结果中的编号 → 写入"技术详情"提示用户核实 |
| **引用核对提示** | `routers/chat.py` | 引用编号被剔除、或正文出现不在检索结果里的编号时，在正文顶部加一条"⚠️ 引用核对：…不在本次检索到的条款中…"，并把具体编号写进技术详情 |
| **追问时清空追问列表** | `routers/chat.py` | `need_clarification = false` 时，`followup_questions` 一律清空 |
| **补免责声明** | `guard.ensure_disclaimer` | 每条答案都必须含"不构成正式测评结论" |

**为什么 `found` 要由服务端决定**：
实测 qwen2.5 会把"我还想多问几句"表达成"知识库中未找到"，
导致【共用账号】这类**明明检索到条款**的问题，用户被告知"没找到"，直接被带偏。
知识库里到底有没有，检索分数比模型的自我判断可靠得多。

**但"分数高"不等于"该答"**——这是这一版新增的认识。
库外法规题和适用性判定题的检索分数都很高（实测 0.53~0.97），
阈值闸门对它们完全无效。所以必须在"检索之后、调模型之前"再加一层
基于**问题文本本身**的判定（`app/scope.py`），而不是继续加高阈值。

## 三、引用编号的解析规则

模型写的编号形式五花八门，`guard.py` 按下面的顺序尝试解析：

| 顺序 | 输入形态 | 处理 |
|---|---|---|
| 1 | `8.1.4.1` | 精确匹配 |
| 2 | `8.1.4.1 身份鉴别（标识与口令复杂度）` | 提取开头编号（`extract_clause_id`） |
| 3 | `A03:2021-CWE-89` / `PR.AA-01` | 按格式提取 |
| 4 | 前缀/后缀不完全一致 | 尝试前缀匹配 |
| 5 | `条款1` / `第2条` / `条款三` | 位置序号 → 翻译成检索结果里的第 N 条 |
| 6 | 以上都不行 | 剔除，记入技术详情 |

### 正文里的位置序号也要翻译

模型在正文里写"根据【条款1】【条款2】的要求"时，
`rewrite_positional_refs()` 会替换成"根据【8.1.4.1 身份鉴别】【PR.AA-01 身份管理与访问控制】的要求"。

**实现注意（踩过坑）**：正则必须收紧，只认 `条款N`、`条款三`、`第N条` 三种写法，
否则会把"第一，要检查…""第三次登录失败""这是第一次做自查"这类正常中文误改。

## 四、⚠️ 风险判定的证据规则

**三类高风险**：`encryption` / `access_control` / `personal_info`。

判定采用**三方证据、权重不同**的策略：

| 证据 | 来源 | 采信规则 |
|---|---|---|
| 证据2 | 用户问题里出现高风险词表中的词 | **直接采纳** |
| 证据3 | **被引用的**条款自带该 `risk_tag` | **直接采纳** |
| 证据1 | 模型自报的 `risk_tags` | **必须有佐证才采纳**——问题或引用条款的文本里要能找到相关词 |

### 为什么要给模型自报加限制

实测 qwen2.5 有**"见谁都标"**的倾向：一次回答输出 5 个标签，三类风险全上，
甚至同一个标签重复 3 次。如果全盘采信，结果是**每条回答都挂三个 ⚠️**，
⚠️ 就彻底失去提示意义——用户会直接无视它。

### 修改前后的实测对比

| 问题 | 修改前 | 修改后 |
|---|---|---|
| 没做备份 | ⚠️ 三类全标 | 无标注 ✓ |
| 服务器没打补丁 | ⚠️ 三类全标 | 无标注 ✓ |
| 账号共享 | ⚠️ 三类全标 | ⚠️ 访问控制 ✓ |
| 手机号没加密 | ⚠️ 三类全标 | ⚠️ 数据加密 + 个人信息保护 ✓ |
| HTTP 明文传输 | ⚠️ 三类全标 | ⚠️ 数据加密 ✓ |
| 系统日志保存多久 | 无 | 无 ✓（日志不属于三类高风险） |

### 一个容易踩的坑

证据3 **只能看被引用的条款**，不能把"检索到的前 3 条"也算进来。
否则问"备份""打补丁"时，只要召回的条款里混进一条带 `encryption` 标签的，
就会把三类风险全标上。

## 五、结构化输出格式

用 Ollama 的 `format` 参数传 JSON Schema，约束解码：

```json
{
  "answer": "给用户看的正文，中文，大白话",
  "citations": ["8.1.4.1", "PR.AA-01"],
  "risk_tags": ["access_control"],
  "need_clarification": false,
  "followup_questions": [],
  "found": true
}
```

**设计取舍**：`citations` 用**纯字符串数组**，不用嵌套对象。
实测嵌套对象对 7B 级别的小模型太容易写崩，纯字符串数组最稳。
条款的标题、正文、章节路径都由服务端从检索结果补齐，模型不需要重复给。

## 六、降级策略

| 失败点 | 表现 | 降级行为 | 用户看到 |
|---|---|---|---|
| Ollama 没启动 | 连接失败 | 只列条款，不做总结 | 橙色标记"大模型不可用，已降级为条款检索" |
| 模型没下载 | HTTP 404 | 同上，并提示下载命令 | 同上 + 提示 `ollama pull xxx` |
| 生成超时 | ReadTimeout | 同上，提示可调大 `LLM_TIMEOUT` | 同上 |
| 返回非法 JSON | 解析失败 | 用容错解析，**只从坏掉的结构里抠 `answer` 字段**（`llm.salvage_answer_field`）；抠不出来就丢弃这段模型输出，降级为纯条款检索 | 技术详情里记一条"模型输出不是合法 JSON"；**绝不会看到 `{` 开头的结构文本** |
| 语义模型加载失败 | 异常 | 只走关键词检索 | 知识库页显示"未启用"，功能不中断 |
| 检索无结果 | 分数低于阈值 | **不调模型**，直接拒答 | 红色标记"知识库中未找到对应条款" |

**原则：任何单点失败都不能让用户看到白屏或英文堆栈。**

## 七、改提示词的正确流程

提示词是这个软件里**改动风险最高**的文件。改之前：

```
1. 先想清楚：要解决什么具体问题？有没有实测案例？
2. 在本文档对应章节写清楚改成什么、为什么改
3. 改 app/prompt.py
4. 跑 .venv\Scripts\python.exe tests\run_eval.py --llm（必须带 --llm，否则测不到提示词）
5. 重点检查这几类：
   - 拒答题是否仍然拒答（10/10 是死线）
   - 具体情形的问题是否直接回答（不能被误判成"需要追问"）
   - 笼统问题是否追问（且不说"找不到"）
   - 引用编号是真编号，不是"条款1"
   - ⚠️ 标注精准，不是三类全上
6. 记 devlog 的「问题与决策」
```

**每次只改一条规则。** 一次改三条，出问题根本不知道是哪条引起的。

## 九、第四轮（2026-10-19）：等级判定与条文标注落在哪一行代码

前三轮修的是"把红队举过的那几句话加进词表"，结果是每加一批、红队换一种写法又绕过。
第四轮改的是**判定依据本身**。这一节只写代码里能查到的位置：每条给出函数名与文件行号，
指不到具体函数的结论一律不写——改坏了直接看那一行。

### 9.1 等级锚点闭集：不再枚举"三级怎么写"

`app/scope.py:452` 的 `_LEVEL_ANCHOR` 只认一个闭集：

```python
_LEVEL_ANCHOR = re.compile(
    r"(级|級|[Ll]v?\s*-?\s*\d|Level\s*-?\s*\d|(?<![A-Za-z0-9])[Tt]\s*-?\s*\d)", re.I
)
```

为什么是闭集：中文里任何等级表达都绕不开「级 / 級」（三级、第3级、叁级、等级3、第三等级）；
英文变体一定带 L / Lv / Level / T + 数字（L3、Lv3、Level-3、T3）。所以锚点不需要知道
"这句话怎么表达等级"，只需要知道"这句话里有没有等级"。语言可以无限变，这个闭集不会变。

教训：第一到第三轮都在枚举写法（`三级|第三级|L3|T3|…`），红队补一种就绕过去一次。
把"等级的所有写法"当成有限集合，这个前提本身就是错的。

锚点单独出现还不够，否则「A 级机房」「三级菜单」会被误伤：

- `_LEVEL_CONTEXT`（`app/scope.py:457`）：等保 / 等级保护 / 定级 / 分级 / 测评 / 备案 / 保护等级 / 安全等级；
- `_LEVEL_DIRECTIVE`（`app/scope.py:460`）：`按|按照|做到|建到|建设到|整改到|达到|评到|定到` + 锚点；
- `_LEVEL_KNOWLEDGE`（`app/scope.py:466`）：知识型问法白名单（有哪些 / 怎么规定 / 区别 / 定义…）；
- `_LEVEL_STATEMENT`（`app/scope.py:477`）+ `_LEVEL_SOLVE`（`app/scope.py:482`）：把
  「已经定级为三级，问后续流程」与「已经定了三级，还要按几级整改」分开；
- 取值入口 `_level_anchor_hit()`（`app/scope.py:489`）。

### 9.2 回答侧滑动窗口兜底：`guard.strip_level_conclusions`

前置闸门只管"问法"，管不住模型自己在正文里写「你们应当按三级建设」。兜底在
`app/guard.py:576` 的 `strip_level_conclusions(text) -> (text, removed)`：按
`_SENTENCE_SPLIT` 逐句扫描，命中条件是三件事同时成立——

1. **本句或上一句**含用户指代（`_USER_REF`，`app/guard.py:546`：您 / 你们 / 贵司 / 我们公司 / 这套系统…）；
2. 本句含等级锚点（`_LEVEL_ANCHOR`，`app/guard.py:551`，与 scope 同一闭集）；
3. 本句含判断词（`_LEVEL_JUDGE`，`app/guard.py:555`：建议 / 应当 / 需要 / 属于 / 按…建设…）。

"上一句"就是滑动窗口：模型常写成「贵司的系统属于第三级。」拆在两句里，只看本句会漏。
命中后删掉该句、换成中性说明 `_LEVEL_CONCLUSION_NOTE`（"…本工具不替您下这个结论。"），
返回 `removed=True`。调用点在 `app/routers/chat.py:534`：命中即把整条回答降级为
`mode="needs_context"`、`found=False`、零引用，并追加 note。

两条护栏（任一成立就不删）：

- **疑问句不删**：`_QUESTION_GUARD`（`app/guard.py:562`），句中有 `？/?` 或 哪些 / 什么 / 怎么 / 如何 / 是否——
  那是系统在反问用户补充信息，不是替用户拍板；
- **主语是标准本身不删**：`_STANDARD_SUBJECT` / `_STANDARD_STRUCT`（`app/guard.py:564` / `:567`），
  句首是 等保 / 标准 / 条款 / 要求 / 规定 / 规范，或"标准里 / 要求中"结构——那是在介绍标准。

另有拆句式 `hit_split`（`app/guard.py:604`）：上一句有用户指代、本句 ≤24 字、且是
「等级为 X / 属三级」的系词句，同样删。

### 9.3 前置判定默认拒绝：锚点 + 等保语境，知识型白名单除外

`app/scope.py:548-558` 是闭集兜底：`_level_anchor_hit()` 命中，且
（`_LEVEL_CONTEXT` 或 `_LEVEL_DIRECTIVE` 命中），且不在 `_LEVEL_KNOWLEDGE` 白名单里，
就返回"不可判定"，走 `needs_context`（不定级 + 追问），**不调用模型**。
方向是默认拒绝：漏判 = 替用户下结论，多拦 = 多问一句；两者的代价不对称，
所以代码选择"宁可多拦"。

陈述式等级（`_LEVEL_STATEMENT` 且无 `_LEVEL_SOLVE`）在 `app/scope.py:505` 就提前放行；
知识型问法只豁免"要不要做等保/测评"那一条（`app/scope.py:511`），其余枚举模式照常生效。

### 9.4 清单外条文转述就地标注：`guard.annotate_unverified_clause_claims`

知识库编号是 `8.1.4.1` / `PR.AA-01` / `A01:2021`，没有"第X条"这种形式；正文出现
「第十三条规定…」几乎一定是模型凭记忆转述库外法规。`app/guard.py:632` 的
`annotate_unverified_clause_claims(text) -> (text, marked)` 用 `_CLAUSE_CLAIM`
（`app/guard.py:625`）逐句匹配，命中就给该句加前缀 `_UNVERIFIED_PREFIX`
（"（以下内容不是知识库依据，仅供定位参考："），返回标注句数。

**接入点**：`app/routers/chat.py:496` 在答案拼接路径上直接消费返回值——
`answer_text, unverified_clauses = guard.annotate_unverified_clause_claims(answer_text)`，
命中数写进 notes（「回答中有 N 处「第X条」式条文转述，已标注为「不是知识库依据」」）。
刻意不放进前端折叠的"技术详情"：用户不会展开备注去发现条文是编的。

### 9.5 验收方式：矩阵，不是红队原句

`tests/test_level_denial.py`（20 条用例）：

- `test_matrix_blocked` 用 `LEVELS × ACTIONS × SUBJECTS` 在运行时生成 240 句，
  要求全部 `mode=needs_context` 且 `llm_calls` 合计为 0；
- `test_positive_matrix` 的 6 条知识问法必须照常作答（且确实调了模型）；
- 回答侧 18 条等级结论句必须删除或改写，6 条知识型输出原样保留；
- 两条护栏、RT18-06（条文标注）、RT18-05（价格类）、RT18-04（繁简/日文/不可见字符）
  各一条。

该套件用 `llm_calls` 打桩、不依赖 Ollama；从 2026-10-19 起在
`.github/workflows/ci.yml` 的「等级判定矩阵（锚点闭集 + 回答侧兜底）」步骤里执行
（`run: python tests/test_level_denial.py`）。

## 十、第七轮（2026-10-19）：答案正文不再由模型生成

### 10.1 为什么改结构，而不是再打一轮补丁

前六轮都在做同一件事：让模型写出的话里「判断用户的情况」那几句被删掉。
每一轮红队都能用一批**新的、没人见过的**句子打穿它——第四轮的
`按L3建设可以吗`、第五轮的 `tier-3`、第六轮的 `第三档比较合适。`／`等保可以先放一放。`。

两批互不相交的句子得出同一个结论：**「逐句判断这句话的主语是用户还是标准」
不是一个能在字符串层面收敛的问题。** 只要模型还在自由写句子，就永远有下一种写法。

所以第七轮换了位置：**模型不再写答案正文。**

### 10.2 现在的分工

| 谁 | 产出 |
|---|---|
| 模型 | 只输出结构化字段：`found` / `clauses`（条款编号）/ `summary`（≤120 字一句话概述）/ `risk_tags` / `followup` / `need_clarification` |
| 服务端 `app/answer.py` | 拼装最终答案：固定开场 → 逐条条款块（编号 + 标题 + 正文摘录）→（可选）概述 → ⚠️ 风险汇总 → 固定收尾 |

`answer` 与 `citations` 两个字段已从模型输出契约里**删除**。模型没有地方可以写
「你们应当按三级建设」，因为它根本不参与写答案。

### 10.3 概述（`summary`）的两道闸

唯一的自由文本是那句概述，所以两道闸都下在这里：

1. **判定闸** `summary_reject_reason(summary) -> str | None`：
   空 / 超长 / 含等级写法 / 含档位写法 / 含第二人称 / 含判定或允许词 /
   含许可免除结论 / 含价格机构表述 / 疑问句 —— 命中任一条即**整条丢弃**。
2. **接地闸** `grounding_hit()`：概述的实词 token 必须与它引用的条款
   （title / text / summary）至少有一个交集，否则以「与所引条款没有交集」丢弃。
   停用词排除「要求 / 应当 / 企业 / 系统 / 进行 / 可以 / 相关」这类泛词，
   否则随便一句空话都能蹭出交集。

**概述被丢弃不影响答案完整性**：条款清单、风险标注、收尾照常渲染，
只是少那一句话。这是有意的降级方向。

### 10.4 一个已知的代价，写在这里而不是藏着

判定闸用的是**整条丢弃**，所以会误杀一部分合规的概述。实测（12 条合规知识型概述）
**误杀 4 条 / 12（33%）**，其中：

- `安全审计记录应当覆盖重要用户行为和重要安全事件。` —— 撞「应当」
- `标准要求对数据进行分类分级管理。`、`等保要求做定级备案…`、
  `三级要求里包含安全审计与入侵防范两类控制项。` —— 撞裸「级」

**这个过宽是故意的**：把「等保要求做定级备案」救回来，就等于把 `按三级建设` 一起放回来。
概述只是锦上添花，宁可少说一句。想降误杀只能改判据的形状，**不许**往
`_JUDGE_WORDS` 里加 `即可`（下次就是 `就行` / `也无妨`），也**不许**去掉裸「级」。

### 10.5 验收

`tests/test_answer_render.py`（12 条用例）钉住三件事：概述命中判定闸必须整条丢弃、
空话过不了接地闸、丢弃后条款块与收尾必须完整。它在
`.github/workflows/ci.yml` 的「服务端答案拼装与概述过滤」步骤里跑。
