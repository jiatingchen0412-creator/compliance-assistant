# 05 · 问答与防幻觉规范

> 这个软件的**生命线**是"不编造条款号"。这份文档规定它该怎么回答、怎么引用、
> 什么时候该拒答、什么时候该追问。**改提示词之前必须看这里。**

---

## 一、回答的六条规则

这六条对应 `app/prompt.py` 里的 `SYSTEM_PROMPT`，是给大模型的硬性约束。
**编号与提示词正文里的【规则N】一一对应，改一边就要改另一边。**

> **总原则：提示词只是"请它别这么干"，代码才是"让它干不成"。**
> 凡是"答错了会严重误导用户"的行为（编造条文、替用户做适用性判定、
> 把笼统问题当成已知情况回答），必须由服务端代码拍板——
> 因为只有代码里的保证才能被**离线测试**证明（`tests/test_scope.py`、
> `tests/test_guard.py` 不需要 Ollama 就能跑）。

### 规则1 · 引用只能来自【可用条款】

- 回答只能引用本次检索到的条款编号
- 引用时必须写**条款编号本身**（`8.1.4.1`、`PR.AA-01`、`A01:2021`）
- **绝对不许**写成"条款1""第1条"这种序号（序号只是给模型看的，用户看不懂）
- 不许编造条款号，不许编造条款内容

### 规则2 · 照着【可用条款】回答，不许自由发挥

判断标准只有一个：**【可用条款】里有没有和用户问题相关的条款**。

| 情况 | `found` | 回答怎么写 |
|---|---|---|
| 有相关条款（哪怕不完全对应他的具体情况） | `true` | 必须引用这些条款、说明要求什么。**不许说"未找到"** |
| 完全无关（用户问天气、电影） | `false` | 明确说"知识库中未找到…"，建议咨询专业安全顾问 |

> **这条规则被"矫枉过正"过一次，教训值得留着**：
> 为了修"明明检索到了却说找不到"，旧版规则2 写成过
> "只要有一点点相关就一律 found=true，**绝对不许**说知识库中未找到"。
> 结果连"用户问的是知识库里根本没有的法规"这种真正该拒答的情形
> 也被一并封死了——于是模型开始凭记忆编造《个人信息保护法》的条文。
> 现在的写法把两件事分开：**"库里有没有"只看【可用条款】**，
> 而**"能不能转述库外法规的内容"是另一回事**（见规则2b）。

### 规则2b · 库外法规只说明"未收录"，绝不转述它的内容

用户点名了知识库没收录的法规（《个人信息保护法》、GDPR、ISO 27001…）时：

- 只能说"本工具未收录这部法规"并建议查阅官方文本或咨询顾问
- **绝不转述它的条文内容、条号含义、适用范围**——哪怕模型"记得"
- 服务端还会再兜一道：`guard.strip_out_of_kb_claims()` 会按句删掉
  转述库外法规的句子（见第二节）

> **为什么必须有这条**：这类编造最难被发现——模型会一边编《个人信息保护法》
> 第 13 条的内容，一边挂上**真实存在**的等保引用编号，
> 用户根本分辨不出哪句有据可查。实测 3/3 稳定复现，
> 而且编出来的内容本身就是错的（把第 5/6 条的原则安到了第 13 条上）。

### 规则3 · 高风险必须标注

涉及数据加密 / 访问控制 / 个人信息保护三类主题时，`risk_tags` 必须填对应值，
并在正文里用 ⚠️ 开头的句子单独说出来。

### 规则4 · 信息不足才追问，追问不等于拒答

**`found` 和 `need_clarification` 是完全独立的两件事**：

```
found              = 知识库里有没有相关条款
need_clarification = 用户描述够不够具体
```

| 情况 | 判断 | 该怎么做 |
|---|---|---|
| **A. 已描述具体情形**<br>（"共用管理员账号""手机号没加密""离职权限没回收"） | `need_clarification = false` | 直接给：结论 + 条款依据 + 2-4 条自查动作 |
| **B. 只说了很笼统的话**<br>（"我们系统安全吗""合规难不难"） | `need_clarification = true` | 仍然 `found = true`，仍然引用条款并说明大致管什么，**然后再问** 1-3 个具体问题 |

**任何时候都不许把"我需要更多信息"表达成"知识库里没有"。**

> **实测 7B 模型经常漏做这条**：问"我们的数据安全吗？""要不要做等保？"
> 它直接给一段泛泛的结论，一个反问都没有。而这段结论读起来是
> "已经看过你的情况了"的口吻，用户会当真。
> 所以服务端加了确定性兜底：`scope.needs_clarification()`
> 在"问题很短 + 命中了笼统问法 + 完全没提具体情形"三条同时成立时，
> 强制补上追问，并在回答最前面加一句"您说的情况还比较笼统"。
> 判定刻意**写得窄**——误判（用户问了具体问题却被反问一圈）比漏判更烦人。
> `tests/test_scope.py` 里既有 4 道"必须追问"的题，也有 8 道"必须不追问"的对照。

### 规则5 · 不替用户做适用性判定

"哪些条款不适用""这条对我们适用吗""哪些要求没覆盖"这类问题，
必须结合用户系统的**定级结果、业务范围、部署模式**逐条比对才能判断。
在用户没有提供这些信息时：

- 不要罗列条款编号当作"不适用条款清单"——这是最容易出错、也最误导人的做法
- 应说明"这无法在不了解您系统具体情况的前提下判定"，并建议做正式适用性分析

> 这类问题**在 `chat.py` 里根本不调模型**：命中后直接返回服务端模板
> （`scope.needs_context_answer`）。理由见 `app/scope.py` 的模块注释——
> 让模型去编一份条款清单只会害人。

## 二、服务端强制修正（比提示词更可靠）

提示词是"请求"，服务端校验才是"强制"。以下是代码层面的硬规则：

| 规则 | 位置 | 说明 |
|---|---|---|
| **阈值拒答** | `retrieval.py` | 最高分 < `RETRIEVAL_MIN_SCORE`（0.40）→ 直接返回"未找到"，**根本不调大模型** |
| **库外法规识别** | `scope.detect_out_of_kb` | 在**阈值闸门之前**判定；命中后服务端强制拼一段"该法规未收录"说明在最前面，模型删不掉 |
| **清理库外法规转述** | `guard.strip_out_of_kb_claims` | 按句删掉转述库外法规内容的句子。**顺序关键：先清模型的、再拼服务端的**，反了会误伤服务端那段说明（它自己就带法规名） |
| **适用性判定不调模型** | `routers/chat.py` | 命中 `scope.needs_system_context` → 直接用服务端模板回答，`mode="needs_context"` |
| **缺信息时强制追问** | `scope.needs_clarification` | 服务端单向补位：模型说要追问就尊重它，模型漏了而规则有把握时才补上 |
| **`found` 由服务端拍板** | `routers/chat.py` | 能调到模型说明检索命中了 → `found` 一律为 `true`，**不听模型的** |
| **剔除非法引用** | `guard.validate_citations` | 模型给的编号逐个比对检索结果，对不上的剔除并记入技术详情 |
| **正文编号扫描** | `guard.detect_hallucinated_ids` | 正文里出现不在检索结果中的编号 → 写入"技术详情"提示用户核实 |
| **矛盾清理** | `guard.strip_false_no_result` | 模型声称"未找到"但服务端判定找到时，删掉正文里矛盾的句子 |
| **追问时清空追问列表** | `routers/chat.py` | `need_clarification = false` 时，`followup_questions` 一律清空 |
| **补免责声明** | `guard.ensure_disclaimer` | 每条答案都必须含"不构成正式测评结论" |

**为什么 `found` 要由服务端决定**：
实测 qwen2.5 会把"我还想多问几句"表达成"知识库中未找到"，
导致【共用账号】这类**明明检索到条款**的问题，用户被告知"没找到"，直接被带偏。
知识库里到底有没有，检索分数比模型的自我判断可靠得多。

**但"分数高"不等于"该答"**——这是这一版新增的认识。
库外法规题和适用性判定题的检索分数都很高（实测 0.53~0.97），
阈值闸门对它们完全无效。所以必须在"检索之后、调模型之前"再加一层
基于**问题文本本身**的判定（`app/scope.py`），而不是继续加高阈值。

## 三、引用编号的解析规则

模型写的编号形式五花八门，`guard.py` 按下面的顺序尝试解析：

| 顺序 | 输入形态 | 处理 |
|---|---|---|
| 1 | `8.1.4.1` | 精确匹配 |
| 2 | `8.1.4.1 身份鉴别（标识与口令复杂度）` | 提取开头编号（`extract_clause_id`） |
| 3 | `A03:2021-CWE-89` / `PR.AA-01` | 按格式提取 |
| 4 | 前缀/后缀不完全一致 | 尝试前缀匹配 |
| 5 | `条款1` / `第2条` / `条款三` | 位置序号 → 翻译成检索结果里的第 N 条 |
| 6 | 以上都不行 | 剔除，记入技术详情 |

### 正文里的位置序号也要翻译

模型在正文里写"根据【条款1】【条款2】的要求"时，
`rewrite_positional_refs()` 会替换成"根据【8.1.4.1 身份鉴别】【PR.AA-01 身份管理与访问控制】的要求"。

**实现注意（踩过坑）**：正则必须收紧，只认 `条款N`、`条款三`、`第N条` 三种写法，
否则会把"第一，要检查…""第三次登录失败""这是第一次做自查"这类正常中文误改。

## 四、⚠️ 风险判定的证据规则

**三类高风险**：`encryption` / `access_control` / `personal_info`。

判定采用**三方证据、权重不同**的策略：

| 证据 | 来源 | 采信规则 |
|---|---|---|
| 证据2 | 用户问题里出现高风险词表中的词 | **直接采纳** |
| 证据3 | **被引用的**条款自带该 `risk_tag` | **直接采纳** |
| 证据1 | 模型自报的 `risk_tags` | **必须有佐证才采纳**——问题或引用条款的文本里要能找到相关词 |

### 为什么要给模型自报加限制

实测 qwen2.5 有**"见谁都标"**的倾向：一次回答输出 5 个标签，三类风险全上，
甚至同一个标签重复 3 次。如果全盘采信，结果是**每条回答都挂三个 ⚠️**，
⚠️ 就彻底失去提示意义——用户会直接无视它。

### 修改前后的实测对比

| 问题 | 修改前 | 修改后 |
|---|---|---|
| 没做备份 | ⚠️ 三类全标 | 无标注 ✓ |
| 服务器没打补丁 | ⚠️ 三类全标 | 无标注 ✓ |
| 账号共享 | ⚠️ 三类全标 | ⚠️ 访问控制 ✓ |
| 手机号没加密 | ⚠️ 三类全标 | ⚠️ 数据加密 + 个人信息保护 ✓ |
| HTTP 明文传输 | ⚠️ 三类全标 | ⚠️ 数据加密 ✓ |
| 系统日志保存多久 | 无 | 无 ✓（日志不属于三类高风险） |

### 一个容易踩的坑

证据3 **只能看被引用的条款**，不能把"检索到的前 3 条"也算进来。
否则问"备份""打补丁"时，只要召回的条款里混进一条带 `encryption` 标签的，
就会把三类风险全标上。

## 五、结构化输出格式

用 Ollama 的 `format` 参数传 JSON Schema，约束解码：

```json
{
  "answer": "给用户看的正文，中文，大白话",
  "citations": ["8.1.4.1", "PR.AA-01"],
  "risk_tags": ["access_control"],
  "need_clarification": false,
  "followup_questions": [],
  "found": true
}
```

**设计取舍**：`citations` 用**纯字符串数组**，不用嵌套对象。
实测嵌套对象对 7B 级别的小模型太容易写崩，纯字符串数组最稳。
条款的标题、正文、章节路径都由服务端从检索结果补齐，模型不需要重复给。

## 六、降级策略

| 失败点 | 表现 | 降级行为 | 用户看到 |
|---|---|---|---|
| Ollama 没启动 | 连接失败 | 只列条款，不做总结 | 橙色标记"大模型不可用，已降级为条款检索" |
| 模型没下载 | HTTP 404 | 同上，并提示下载命令 | 同上 + 提示 `ollama pull xxx` |
| 生成超时 | ReadTimeout | 同上，提示可调大 `LLM_TIMEOUT` | 同上 |
| 返回非法 JSON | 解析失败 | 用容错解析；再失败就把原文当答案 | 技术详情里记一条"模型输出不是合法 JSON" |
| 语义模型加载失败 | 异常 | 只走关键词检索 | 知识库页显示"未启用"，功能不中断 |
| 检索无结果 | 分数低于阈值 | **不调模型**，直接拒答 | 红色标记"知识库中未找到对应条款" |

**原则：任何单点失败都不能让用户看到白屏或英文堆栈。**

## 七、改提示词的正确流程

提示词是这个软件里**改动风险最高**的文件。改之前：

```
1. 先想清楚：要解决什么具体问题？有没有实测案例？
2. 在本文档对应章节写清楚改成什么、为什么改
3. 改 app/prompt.py
4. 跑 .venv\Scripts\python.exe tests\run_eval.py --llm（必须带 --llm，否则测不到提示词）
5. 重点检查这几类：
   - 拒答题是否仍然拒答（5/5 是死线）
   - 具体情形的问题是否直接回答（不能被误判成"需要追问"）
   - 笼统问题是否追问（且不说"找不到"）
   - 引用编号是真编号，不是"条款1"
   - ⚠️ 标注精准，不是三类全上
6. 记 devlog 的「问题与决策」
```

**每次只改一条规则。** 一次改三条，出问题根本不知道是哪条引起的。

## 八、必须永远成立的测试用例

改任何东西之后，这五条都必须通过（已包含在 `tests/eval_questions.json`）：

| 输入 | 期望行为 |
|---|---|
| "推荐几部好看的电影" | 拒答，说"知识库中未找到"，建议咨询顾问 |
| "帮我写一首诗" | 拒答 |
| "我们公司十几个人都用同一个管理员账号登录" | 直接回答 + 引用真实条款号 + ⚠️ 访问控制 |
| "客户的手机号存在数据库里，没有做加密" | 直接回答 + ⚠️ 数据加密 + ⚠️ 个人信息保护 |
| "我们的系统安全吗" | `need_clarification = true` + 给出 1-3 个问题 + **不说"未找到"** |
| "帮我看看 8.1.4.1 讲了什么" | 正确引用 `8.1.4.1` |
