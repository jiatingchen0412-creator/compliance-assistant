# 06 · 开发步骤与里程碑

> 这份文档规定**怎么推进这个项目**：先做什么、后做什么、每一步做到什么程度算完成。
> 核心原则一句话：**一次只做一件事，每件事都要能验证、能回退。**

---

## 一、工作循环（每次开发都按这个来）

```
① 开工前   → 在 devlog/当天.md 的「今日目标」写清楚这次要做什么
② 只做一步 → 按本文档的步骤编号，一次只推进一个步骤，不顺手改别的东西
③ 自测     → 跑 .venv\Scripts\python.exe tests\run_eval.py，指标不能退步
④ 真实验收 → 打开浏览器亲手用一遍，确认不是"测试通过但用不了"
⑤ 记录     → devlog 写「已完成」和「问题与决策」
⑥ 交给你看 → 停下来汇报，等你确认后再进下一步
```

**第 ⑥ 步不能省。** 每一步做完都要停下来让你看一眼，确认方向没跑偏再继续。

---

## 二、三条铁律

| 铁律 | 说明 | 为什么 |
|---|---|---|
| **一步只动一个模块** | 改检索就只改检索，别顺手把界面也改了 | 出问题时能立刻知道是哪次改动引起的 |
| **不跑评测不算完成** | 任何改动都要跑 `tests/run_eval.py` | 这个项目的核心是"答得准不准"，没有指标就是拍脑袋 |
| **规范变了先改 docs** | 想改行为约定，先改 `docs/` 再改代码 | 否则过两周没人记得当初为什么这么设计 |

### 指标红线（任何一步都不能跌破）

| 指标 | 红线 | 当前值 |
|---|---|---|
| 检索召回率 | ≥ 27/29 | 29/29 |
| 拒答正确率 | **必须 5/5** | 5/5 |
| ⚠️ 风险标注率 | ≥ 8/9 | 9/9 |
| 库外法规识别率 | **必须 6/6** | 6/6 |
| 适用性判定拦截率 | **必须 4/4** | 4/4 |
| ⚠️ 误标率 | **误标 ≤ 0 处** | 0/2 |
| 单次回答耗时 | ≤ 10 秒 | 1.3 ~ 4.3 秒 |

「拒答正确率」「库外法规识别率」「适用性判定拦截率」是三条"一票否决"的指标——
宁可答"找不到"，也绝不能编造条款、更不能替用户做适用性判定。

改红线之前先改 `docs/07-测试与验收规范.md`。数量本身也要卡
（`app/quality.py` 的 `EXPECTED_COUNTS`）：只看通过数的话，题库被删掉一半
反而会显示"全部达标"。

## 七半、v1.4 · 可信度修复（防幻觉二期）✅ 已完成

> **背景**：2026-10-08 的审计发现，防幻觉机制只防住了"检索不到"，
> 没防住"用户点名知识库以外的法规"。实测 3/3 稳定复现：
> 问「《个人信息保护法》第 13 条具体怎么规定的？」，系统 `found=True`，
> 引用等保 `8.1.4.26/27/28/34`，回答直接陈述"第 13 条规定了合法性、
> 正当性、必要性原则"——**条文内容本身是错的**（那是第 5/6 条的内容），
> 而且挂着真实存在的等保引用，用户根本分辨不出来是编的。
>
> **根本设计原则**：**确定性优先**。关键保证不交给 7B 模型拍板，
> 能用服务端代码拍死的就拍死。附带的巨大好处是这些保证**可以离线验证**——
> 不启动 Ollama 也能跑测试证明它成立。

| 步骤 | 做了什么 | 验证结果 |
|---|---|---|
| **P5-1** 库外法规拒答 | 新增 `app/scope.py`：`OUT_OF_KB_REGULATIONS` 收录 17 部知识库外的法规/标准（PIPL、网络安全法、数安法、密码法、GB/T 35273、ISO 27001、GDPR、PCI DSS、SOC 2、等保扩展要求等）及其别名；`detect_out_of_kb()` 在**阈值闸门之前**判定；`out_of_kb_notice()` 由服务端强制拼在回答最前面（先说"我不能转述"、再说"库里有什么"、最后给建议）；`guard.strip_out_of_kb_claims()` 按句删除模型转述库外法规的内容（**先清模型的、再拼服务端的**，反了会误伤服务端说明） | `tests/test_scope.py` 9/9、`tests/test_guard.py` 11/11 |
| **P5-2** 不可判定问题识别 | `scope.needs_system_context()` 用 4 条正则识别"哪些条款不适用/这条适用吗"这类必须结合具体系统才能回答的问题；命中后 **`chat.py` 刻意跳过模型**，直接用 `scope.needs_context_answer()` 服务端模板回答（说明为什么无法判定 + 追问定级与部署情况 + 建议做正式适用性分析），`need_clarification=True`、`mode="needs_context"` | 端到端零编造：回答里不会出现任何"不适用条款清单" |
| **P5-3** 修 ⚠️ 误标 | 根因是 `guard.detect_risks` 的证据1 佐证语料**收得太宽**：原来把被引用条款的 `text` 全文、`summary`、`keywords` 都拼进去，条款正文里提一句"个人信息"、keywords 里带一个"留存期限"，就会让"安全审计"这种问题被标上 `personal_info`。收窄为 `[question, title]`（关键词表是为检索设计的，词面宽是优点；拿来当"要不要标风险"的证据，宽就变成了错）。另从 `data/seed/risk_terms.json` 的 `personal_info.terms` 删掉"留存期限" | ⚠️ 误标率 2/2（0 处误标） |
| **P5-4** 评测集扩到 44 题 | 新增 q31~q44：6 道库外法规题、2 道误标回归题、4 道适用性判定题、2 道需追问题。`expect` 从 `hit/reject` 两种扩为 `hit/reject/out_of_kb/undeterminable` 四种，另加 `risk_forbid`（禁止标注的标签）与 `clarify_expect` | 检索召回 29/29、拒答 5/5、风险标注 9/9、库外法规 6/6、适用性 4/4、误标 0/2 |
| **P5-5** 质量门补严 + 零覆盖模块补测 | **修掉质量门的结构性盲区**：`evaluate_retrieval` 原来用**被评测的同一个阈值**定义"正确答案"（`found = best >= RETRIEVAL_MIN_SCORE`），是闭环自证，结构上不可能发现"阈值过了但不该答"的问题。现在四类 `expect` 各自独立判定，且新增 `EXPECTED_COUNTS` **同时卡数量**（题库被删空反而显示"全部达标"是另一个盲区）。`tests/run_eval.py` 重写为两层：第一层检索层不需要 Ollama、秒级；第二层端到端层需要 Ollama、检查"模型到底有没有真的追问""声明有没有真的出现在回答里"。给零覆盖的 `app/normalize.py` 补测并修掉两个真实缺陷（`tokenize` 的编号残片污染 token 流；`expand_query` 重复计数） | 9 个套件 75 个用例全通过（在 Ollama 未运行状态下跑的，证明不耦合环境） |

**为什么这些保证要写在代码里而不是提示词里**：提示词是"请它别这么干"，
代码是"让它干不成"。7B 模型对训练里见过的热门法条最容易张口就来，
而它的输出会带真实引用编号一起出现，用户无法分辨。

## 十、什么时候应该停下来问你

出现下面任何一种情况，**立刻停下**，不要自己往下做：

1. 需要改动 `data/app.db` 里的**已有数据**（可能丢数据）
2. 需要新增一个**外部依赖**（新库、新服务、新账号）
3. 需要**联网下载**超过 100MB 的东西
4. 发现原有设计有矛盾，改动会波及 3 个以上模块
5. 评测指标跌破红线，且一次修复没成功
6. 你自己也拿不准这样做对不对
