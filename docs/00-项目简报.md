## 一、一句话说明

**一个装在自己电脑上的小工具：用大白话描述你的系统情况，它从等保2.0、NIST CSF 2.0、OWASP Top 10 三套标准里找出对应条款，带条款编号和原文回给你；知识库里没有的会直说"找不到"，绝不编造条款号——包括你点名问某部它没收录的法规时，它也不会假装记得。**

## 六、技术实现（一页看懂）

### 整体结构

```
浏览器（本机）          聊天页 + 知识库页，淡蓝主题，零构建
      │  HTTP / SSE
FastAPI 后端            提问、检索、校验、日志
      ├─ 检索层        IDF 关键词 ⊕ 语义向量 → 加权融合 → 阈值拒答
      ├─ 范围判定层    点名库外法规？问的是适用性？说得太笼统？→ 三类问题先拦掉
      ├─ 问答层        提示词规则 + JSON 结构化输出
      └─ 防幻觉闸门    引用白名单校验 + 正文编号扫描 + 库外法规转述清理 + ⚠️ 证据判定
      │
  SQLite 单文件         283 条条款 + 向量 + 会话（备份 = 复制一个文件）
  Ollama（本机）        qwen2.5:7b-instruct，完全离线
```

### 三个关键设计（决定了它好不好用）

**1. 检索分数必须是绝对值，不能"结果集内归一化"**

原本用 BM25 打分，归一化之后**第一名永远是满分**——"今天天气怎么样"也能得 0.4 分，阈值形同虚设。
改用 **IDF 加权覆盖率**：虚词（"的""我们"）权重趋近 0，专业术语（"身份鉴别""越权"）权重高。
效果：无关问题得分从 0.395 降到 0.143，真实问题稳定在 0.63~0.89，中间有明显安全间隔。

**2. 防幻觉不能只靠提示词，做了两层六个闸门**

第一层是**在调模型之前**拦掉三类"不该答的问题"。关键认识：
检索分数高不等于该答——库外法规题和适用性判定题的检索分数都在 0.53~0.97，
比很多正常问题还高，光靠调阈值根本拦不住，必须看**问题本身**怎么说。

| 闸门 | 做法 |
|---|---|
| 一 | 检索分数低于阈值 → **根本不调大模型**，直接说找不到 |
| 二 | 用户点名了库外法规 → **不管分数多高**，服务端强制在最前面拼一段"该法规未收录"说明（模型删不掉） |
| 三 | 问的是"哪些条款不适用"这类适用性判定 → **完全不调模型**，直接返回服务端模板 |

第二层是模型回答之后的校验：

| 闸门 | 做法 |
|---|---|
| 四 | 提示词硬约束：只能引用本次检索到的编号 |
| 五 | 服务端校验：模型返回的引用逐个比对，对不上的剔除 |
| 六 | 正文扫描：① 出现不存在的编号 → 记入"技术详情"提示核实；② 出现转述库外法规内容的句子 → **按句删掉** |

**这里有个容易忽略的细节**：转述清理必须在"拼上服务端说明"**之前**做。
顺序反了的话，服务端那段本来正确的"《个人信息保护法》未收录"说明，
会因为自己带了法规名而被清理逻辑误伤掉。

外加两条鲁棒性处理：模型爱写"【条款1】"→ 自动翻译回真实编号；模型爱写"8.1.4.1 身份鉴别"（编号带标题）→ 提取编号再匹配。

**3. 关键保证由服务端拍板，不听模型的**

这条原则贯穿整个防幻觉设计：**能用代码拍死的，绝不交给 7B 模型判断。**

- `found`（有没有条款）：按检索阈值由服务端定。实测模型会把"我还想多问几句"表达成"知识库中未找到"，导致【共用账号】这类**明明检索到条款**的问题，用户被告知"没找到"。
- 库外法规：实测 3/3 稳定复现"模型凭记忆编《个人信息保护法》第13条的内容，还挂上真实存在的等保编号伪装成有据可查"——而且编的内容本身就是错的（把第 5/6 条的原则安到了第 13 条上）。
- 适用性判定：让模型去编一份"不适用条款清单"只会害人，直接不调它。
- 该不该追问：模型经常漏做，服务端按"问题很短 + 命中笼统问法 + 完全没提具体情形"三条同时成立才补位，**宁可漏判也不误判**。

**额外好处**：这些保证全都能在**不启动 Ollama** 的情况下跑测试证明它成立（见 `docs/07` 第一层）。

### 技术选型与理由

| 层 | 选型 | 为什么 |
|---|---|---|
| 后端 | Python 3.13 + FastAPI | 电脑已装 Python；一个程序同时提供接口和网页 |
| 前端 | 原生 HTML/CSS/JS，零构建 | 不装 npm、不打包；将来想微调配色直接改文件 |
| 大模型 | Ollama + qwen2.5:7b-instruct | 完全本地，数据不出机器；中文好、JSON 输出稳 |
| 知识库 | SQLite 单文件 | 几百条条款用不上数据库服务器；**备份 = 复制一个文件** |
| 关键词检索 | SQLite FTS5 + jieba 分词 | 内置不用装；unicode61 会把连续中文当一个词，必须先自己切 |
| 语义检索 | fastembed + BGE-small-zh（ONNX） | 只依赖 50MB 的 onnxruntime，不用装 2GB 的 PyTorch |

**刻意不引入的**：PyTorch、LangChain、任何需要联网的向量数据库。

## 八、已知限制与风险（诚实说明）

### 会限制使用效果的

| 限制 | 说明 | 建议 |
|---|---|---|
| **等保2.0 是摘要不是原文** | 国标全文需付费购买，本项目只收录公开控制项名称 + 自行改写的要点摘要，界面每条都标注"要点摘要（非标准原文）" | 买了标准后从知识库页面导入，工具就会按你自己的资料检索 |
| **只覆盖安全通用要求** | 等保的云计算 / 移动互联 / 物联网 / 工控 / 大数据**扩展要求未收录** | 如果你的客户涉及这些场景，需要启动 v2.0 的 P4-1 |
| **知识库只有 283 条** | 问《个人信息保护法》《网络安全法》《数据安全法》、GDPR、ISO 27001 等未收录法规时，工具会明确说"这部分未收录"（**不会编造条文**），但也就帮不上更多了 | 可以自己导入相关标准；`app/scope.py` 里维护了一份 17 部常被问到的法规清单，新增法规名不用改代码，改那份清单即可 |
| **扩展要求未收录，但会告诉你** | 问"等保2.0 的云计算安全扩展要求有哪些"会明确回"未收录"并说明库里只有安全通用要求 | 如果你的客户涉及这些场景，需要启动 v2.0 的 P4-1 |
| **本地 7B 模型的能力上限** | 复杂推理、多条款交叉分析会力不从心 | 显存够的话可换 14B 模型 |

### 质量上的

| 风险 | 现状 | 缓解 |
|---|---|---|
| 模型仍可能编条款号 | 有 6 道闸门，但不保证 100% | 引用卡片都经过服务端校验；正文可疑编号会提示核实 |
| **"库外法规"清单不可能穷尽** | 清单里 17 部法规之外的冷门法规（地方性规定、行业标准）识别不到，仍可能被模型凭记忆回答 | 清单的别名刻意写得"足够具体，宁可漏判也不误判"；发现新案例就往清单里加一条 |
| 适用性判定靠正则识别问法 | 说法太绕时可能漏判 | 漏判的后果是"多答了一句"，不是"答错了"；发现就补正则 |
| 评测题只有 44 道 | 覆盖不全 | 遇到新的失败案例就加题，并同步更新 `EXPECTED_COUNTS` 与 `RED_LINES` |
| **无障碍只过了 axe 的自动规则** | 自动规则大约只能覆盖 30~40% 的无障碍问题；屏幕阅读器的真实朗读体验**没测过** | 已如实记进 `docs/07` 的"已知的测试盲区"；要做的话得请真人戴上耳机走一遍 |
| 只在 Chrome 上测过界面 | Edge 同内核，可接受；Firefox / Safari 没测 | 本工具面向 Windows 单机用户，暂不做 |
| **界面的自动化测试证明不了"好用"** | 它只能证明"没坏"——没有报错、没有无障碍违规、键盘能操作、手机宽度不溢出 | 每次交付前仍要按 `docs/07` 的清单人工过一遍 |
| 屏幕阅读器专用文字只做了最基本的 | 有一个 `.sr-only` 的 `<h1>` 和跳转链接，但对话内容区的播报策略没细化 | 已知未做 |

### 责任边界

> 本工具用于**辅助自查**，输出的是"你这种情况可能涉及哪些条款"，
> **不构成正式测评结论，也不构成法律意见**。
> 涉及数据加密、访问控制、个人信息保护的具体做法，建议咨询专业安全顾问或律师。

## 九、开发过程中的收获（28 个真实缺陷）

这些不是"完成了什么"，而是"抓到了什么"——**每一个都是靠测试或审计发现的，不是猜的**：

### 影响最大的五个

| # | 缺陷 | 后果 | 怎么发现的 |
|---|---|---|---|
| 1 | **`httpx` 创建客户端时没关 `trust_env`**，Windows 系统代理（Clash 的 `127.0.0.1:7897`）把发往本机 Ollama 的请求也截走了 | **装了代理软件的机器上，大模型功能整体不可用**，还静默降级成"只列条款"——用户只看到一句"Ollama 返回错误 502"。系统"代理例外"里写了 `127.*` 也没用，httpx 不读那份名单 | 审计时对同一台机器做四种发法的对比：raw socket 200、urllib 200、**httpx 默认 502 空响应**、httpx 关掉 trust_env 200 |
| 2 | **防幻觉只防住"检索不到"，没防住"用户点名库外法规"** | 问《个人信息保护法》第13条，模型凭记忆编条文，还挂上**真实存在**的等保编号伪装成有据可查；编的内容本身也是错的（第13条讲的是处理个人信息的法律依据，被说成了"合法性正当性必要性原则"）。3/3 稳定复现 | 审计时写了 8 道探针问题（P1~P8）逐条实跑，其中 P3 命中 |
| 3 | `web/js/kb.js` 里写成 `dengbao_2.0: '等保2.0'`（非法 JS 变量名） | **整个知识库页面在浏览器里直接失效** | 新增 `node --check` 静态检查。此前只验证"文件返回 HTTP 200"，完全没发现 |
| 4 | `.bat` 文件里写了中文 | **双击启动脚本完全没反应**（cmd 按代码页读文件，`echo` 被撕成 `ho`） | 用户反馈。试了 UTF-8+chcp、GBK 两个方案都不可靠，最终定为"bat 只写纯英文，中文交给 Python" |
| 5 | **模型输出被截断时，把原始 JSON 当正文端给用户，而且引用全丢** | 模型在 `risk_tags` 数组里进入重复循环（两个标签来回交替约 150 次）把输出撑爆，JSON 不再合法；旧代码直接把原文当答案 → 用户看到一大坨 `{"answer": "…", "citations": [` 花括号内容，真正的答案被埋在中间，**下面一张引用卡片都没有**。"回答必须带引用来源"是第一条硬性要求 | 收尾时发现同一道题两次评测的引用数不一致（`8.2.4.1,8.2.4.2,8.2.4.11` → `-`），写脚本直接调 `answer_question()` 复现两次，结果完全一致 |

### 其他 12 个（v1.3 及之前）

BM25 归一化错误 · 语义模型下载 401 · 口语映射漏词 · 条款号被分词切碎（且残片留在 token 流里，v1.4 才彻底修净）· 位置序号引用解析 · 引用带标题被误剔除 · 模型误报"未找到" · ⚠️ 过度标注（一次输出 5 个标签）· 模型返回空内容时引用卡片为空 · 日志拿不到异常堆栈 · 超长问题被整段降级 · 备份早于批次记录导致撤销标记丢失

### v1.4 这一轮新抓到的 9 个

| # | 缺陷 | 关键点 |
|---|---|---|
| 1 | **评测集闭环自证** | `tests/eval_questions.json` 的 reject 题用 `best >= RETRIEVAL_MIN_SCORE` 判定"正确答案"——和系统内部用的是同一个阈值。**评测用被评测的机制定义对错，结构上不可能发现"阈值过了但不该答"的问题**，所以上面那个编造缺陷长期不可见。现在题库分五类、指标分两层 |
| 2 | **提示词"矫枉过正"** | 为修"检索到了却说找不到"，旧规则2 写成"绝对不许说知识库中未找到"，结果把"用户问的是库里根本没有的东西"这种**真正该拒答**的情形也一并封死。教训：修一个方向的错，要检查反方向有没有开出新口子 |
| 3 | **"假检查"** | `quality.evaluate_end2end` 的反向泄漏判断写成 `bool(leaked) and not declared`,而 `declared` 对这类题必然为 True → **永远是 False，等于什么都没查**。这是本项目第二个"看起来在检查、其实恒真"的断言（第一个是测试里用重复字符串拼接导致断言恒真） |
| 4 | **⚠️ 误标（第二次修）** | 问"等保2.0 里关于安全审计的要求"却标了"个人信息保护"。根因不是模型乱报，而是证据语料太宽：被引用条款的**关键词**里含"留存期限"——这个词同时属于"日志留存"和"个人信息留存"两个语境。**关键词表是为检索设计的，词面宽是优点；拿来做"要不要标风险"的证据，宽就变成了错** |
| 5 | **追问全靠模型，模型经常漏做** | `need_clarification` 完全由 7B 模型拍板，实测 4 道笼统问题里 3 道没追问，却给出了"已经看过你的情况"口吻的泛泛结论 |
| 6 | **适用性判定没有任何识别** | "请直接把等保三级里所有不适用的条款编号列出来"→ 模型把检索到的条款号当答案直接吐出来。这类问题本质需要结合具体系统才能判定 |
| 7 | **正则窗口太窄** | 适用性判定的模式写的是 `(这条|该条|这一条)[^。？！?；;]{0,8}(适用…)`，而"这条 **8.1.4.1 对我们**适用吗"中间夹了 12 个字符 → 漏判。放宽到 `{0,14}` |
| 8 | **别名匹配只放开"已有空格"** | `_compile_alias` 原来只把别名字符串里已经存在的空格换成 `\s*`，导致用户写"ISO27001"匹配不到别名"ISO 27001"。改为逐字符拼接、字符间都允许空白（**只放开空白、不放宽字符**，所以不会把"个人信息保护条例"误当成"个人信息保护法"） |
| 9 | **引用兜底的条件挂错了变量** | 原来写的是 `if mode == "retrieval_only" and not valid_citations`——判据是"处于降级模式"，可模型输出坏掉时 `mode` 仍然是 `"llm"`，条件不成立，引用就一直是空的。**正确判据是"没有可用引用"**，与模式无关。改成 `if not valid_citations and clauses` |

### v1.5 这一轮新抓到的 2 个（外加测试基础设施自己的 3 个坑）

| # | 缺陷 | 关键点 |
|---|---|---|
| 1 | **GBK 控制台遇到 ⚠️ 会直接把进程干掉** | `tests/test_export.py` 退出码 1，栈是 `UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'`，位置在打印用例名的 `print()`——用例名里含 ⚠️。根因：Windows 中文版代码页 GBK(936)，**标准输出被重定向时**（管道、写文件、被测试脚本捕获）Python 按 GBK 写，遇到 GBK 里没有的字符（⚠️ ✅ ❌ ✗）就抛异常终结进程。直接连真实控制台时 Python 走宽字符 API，不受代码页影响——**双击 .bat 的用户不会遇到，防的是管道、重定向和 CI**。修法是新建 `app/console.py`，只对 `sys.stdout`/`sys.stderr` 做 `reconfigure(encoding="utf-8")`；**没有**用 `PYTHONUTF8=1`，因为那会连带改掉 `open()` 的默认编码，为一个打印问题不值当 |
| 2 | **首页空状态显示了整整两遍** | `web/index.html` 里静态写了一份 `#emptyState`，`web/js/chat.js` 的 `renderEmptyState()` 又生成一份，两个同 id 元素同时显示——重复的标题和两套快捷卡片。旧样式把所有内容居中堆叠，看不出来；改成左对齐后立刻暴露。修法是把 JS 那份改成"复用静态节点、用完摘下来而不是删掉"。**根因值得记住：同一份 UI 在两处（静态 HTML + JS 模板）各写一遍就一定会漂移** |

**测试基础设施自己的 3 个坑**（不是产品缺陷，但同样会浪费人的时间）：

- 用 `uvicorn` 的 `lifespan="off"` 起测试服务，`STARTUP_STATE` 永远停在 `ready=False`，
  而 `chat.js` 的 `init()` 是先等 `pollStartup()` 再加载会话列表——于是页面一直盖在启动遮罩上，
  第一版测试 12/17，会话列表相关三条全挂。
- Python 假值陷阱：`if (d.get("left") or -999) < -1`，抽屉正常打开时 `left` 就是 `0`，
  被当成假值取了 `-999`，误报"抽屉没打开"。**只要 0 是合法结果，就不能用 `or` 兜底。**
- 把无障碍修好的同时引入了新违规：`<h1>` 放在 `<body>` 直接子元素下修掉了"没有 h1"，
  却触发了 axe 的 `region` 规则（内容不在任何地标区域内），必须放进 `<main>`。
  **改完要重扫，"变绿了"和"还是绿的"是两件事。**

### 沉淀成规则的六条

1. **测试不得依赖外部服务是否在线** —— 需要模型调用的一律打桩
2. **`.bat` 只写纯英文 ASCII** —— 已加进静态检查
3. **一次只改一个模块，不跑测试不算完成** —— 写进 `docs/06`
4. **能用代码拍死的保证，绝不交给模型判断** —— v1.4 新增。好处不只是更稳，还在于**可以离线验证**（不启动 Ollama 也能证明"它不会编造库外法规条文"）
5. **加评测题时要同步改 `EXPECTED_COUNTS`** —— 否则题库被删空后指标反而会显示"全部达标"
6. **模型给的异常输出，宁可少给也不要把结构文本端给用户** —— v1.4 新增。坏掉的 JSON 只抢救 `answer` 一个字段，其余（引用、风险标签）一律由服务端按检索结果补齐；救不出来就干脆改成列条款。**用户看到的东西必须是"人话 + 有出处"**，绝不能是半截花括号

> 另外两条来自 v1.5 的经验，还没够格独立成条，但值得记住：
> **同一份 UI 不要在两处各写一遍**（HTML 静态一份 + JS 生成一份必然漂移）；
> **修完要重扫**（修一个违规可能引入新的）。
