# 开发日志规范

本目录记录这个项目的**开发过程**：每天做了什么、还剩什么、踩了什么坑、做了什么决定。

## 为什么要有它

项目是边做边调整的，隔几天回来看很容易忘记"当时为什么这么改"。
日志的作用是让每一次决策都有据可查，而不是靠记忆。

## 文件规则

- **一天一个文件**，文件名就是日期：`2026-09-28.md`
- 格式是纯 Markdown，**用记事本就能改**
- 每个文件有五个固定小节：

| 小节 | 写什么 |
|---|---|
| `今日目标` | 开工前写清楚今天要做到什么，做完打勾 |
| `已完成` | 实际完成的事项，带上可验证的结果（例如"召回率 25/25"） |
| `待办` | 还没做的、下次要接着做的 |
| `问题与决策` | 遇到什么问题、最后怎么定的、为什么这么定 |
| `自动记录` | 程序自动写入的（服务启动时间、知识库规模、模型状态） |

## 怎么用

### 自动部分

每次双击 `启动助手.bat` 启动服务时，程序会：
1. 自动创建当天的日志文件（不存在的话）
2. 在 `自动记录` 里追加一条：启动时间、知识库条款数、模型状态

不用人记得去建文件。

### 手动部分

用命令行工具追加：

```bat
.venv\Scripts\python.exe tools\devlog.py done "完成检索阈值标定，召回率 25/25"
.venv\Scripts\python.exe tools\devlog.py todo "给长对话加上下文压缩"
.venv\Scripts\python.exe tools\devlog.py decision "found 改由服务端按阈值判定，不听模型的"
.venv\Scripts\python.exe tools\devlog.py show
.venv\Scripts\python.exe tools\devlog.py summary --days 7
```

或者直接用记事本打开当天文件手写，格式保持一致就行。

## 写作要求

**要写"可验证的结果"，不要写"做了 XX 工作"。**

| ❌ 不好 | ✅ 好 |
|---|---|
| 优化了检索 | 把 BM25 结果集归一化改成 IDF 绝对覆盖率，噪声问题从 0.395 降到 0.143 |
| 修了 bug | 修掉"模型把追问说成未找到"：found 改由服务端按阈值判定 |
| 完成了文档 | 写了 8 份开发规范文档，README 加了索引 |

**待办要写清楚"下一步做什么"，不要写"继续优化"。**

## 和 docs/ 的分工

- `devlog/` —— 过程记录（时间轴：某天做了什么）
- `docs/` —— 标准文档（结论：项目应该是什么样）

规范变了改 `docs/`，改的过程记 `devlog/`。
